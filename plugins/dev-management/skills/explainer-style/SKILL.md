# Explainer — 文章スタイル

技術解説の「**どう書くか**」の文章スタイル原則を定義する Skill。
出典・構造設計はそれぞれ `explainer-citation` と `explainer-structure` に分離されている。
本Skillは「文章レベルの表現」に集中する。

## 想定する読み手

- **Python のコードは読める（書ける）**
- **Git / Linux / シェル / 環境管理 / パッケージングなどの周辺技術は不慣れ**
- 想定領域は汎用的なソフトウェア開発の周辺技術がメイン。随時 Isaac Sim / ROS2 / VLA / embodied AI / AI agents / guardrails などの特化トピックが混ざる
- ゴールは抽象的な理解ではなく、**「どう実装しようか」の道筋が頭に浮かぶこと**

## 内容の重心

- **抽象より具体、網羅より頻出、理論より実装パターン**
- 「なぜそう設計されているか」の背景は簡潔に。**「実務で何をどう書くか」を厚く**扱う
- ツール名の裏にある **メンタルモデル**を最初に共有する（Git なら「スナップショットの有向グラフ」）
- コード例は**動く最小例**。断片ではなく、そのままコピペして動作確認できる粒度で書く
- Python が読み手の共通言語なので、他言語や CLI の説明でも **Python 的な類推**が使えるなら使う
- 長い箇条書きより、**表と短い段落**を優先する

## 到達基準（この Skill の受け入れ基準）

出力された文書は、次の状態を満たさなければならない：

> **読み手が、文書中の任意の用語・任意の文について「これはどういう意味か」と問われたとき、文書内の記述だけを根拠に答えられる状態。**

つまり、文書の中に「意味を問われたら答えられない語・文」が残っていたら未完成。以下の原則はすべてこの到達基準を実現するための手段であり、末尾の「出力前セルフチェック」はこの基準の検査手続きである。

## コア原則

### 原則1：前提知識の補完（最重要）

解説の対象について書く前に、それを理解するために必要な「その分野では当たり前の知識・共通認識」が読み手にあるかを推定する。なさそうな場合は、本文に入る前に **「前提となる文脈」** セクションを 2〜4 行で補う。

❌ **悪い例**（前提なしに本題から始める）：
> この構成では、CI でイメージをビルドしてレジストリに push し、本番のタスク定義を新しいタグで更新する。

✅ **良い例**（前提の足場を先に組む）：
> **前提となる文脈**：コンテナは「アプリと、それが動くのに必要な環境（OS のライブラリ、Python、依存パッケージ）をまとめて固めたもの」で、固めた成果物を**イメージ**、それを動かしている状態を**コンテナ**と呼ぶ。イメージは共有の置き場（**レジストリ**）に置いて配る。以下は、その置き場と実行環境をクラウド上に用意する構成の話になる。

これがないと、テンプレート通りに書いても「結局よく分からない」状態になる。技術的な正確さよりも、**読み手の頭の中に文脈の足場が組めるかどうか** を優先する。

### 原則2：論理の流れを明示する

記述全体が一本の論理線を持つように構成する。各文・各セクションの間の接続を、文中に書き込む。

- 「次に X を行った」ではなく「X を確かめるために Y を行った」
- 「A の結果が出た。B を行った」ではなく「A の結果が出たので、それを踏まえて B を行った」

接続詞（だから / しかし / つまり / なぜなら / 一方で / これに対して）を意図的に使う。読み手が「で、これは何の話だっけ？」と立ち止まらないように書く。

**セクション単位でも同じ**：各セクションの冒頭1文は「前のセクションを受けて、なぜ今からこれを読むのか」を示す。

❌ 「## 実験方法」の冒頭でいきなり「データセットは〇〇を用いた」
✅ 「## 実験方法」の冒頭で「前節の仮説（△△なら□□になるはず）を確かめるには、〜が測れる環境が必要になる。そこで著者らはデータセットに〇〇を選んだ」

### 原則3：平易な表現で言い換える

専門用語が出てきたら、続けて **平易な表現での言い換え** を必ず挟む。術語の並列で「説明したつもり」にならない。

抽象的な記述には、具体例または身近な類比を必ず添える。「A は大きく分けて2種類ある」と書いたら、すぐ後に「たとえば〇〇と〇〇」を続ける。

❌ 「本手法はサンプル効率が高い」（術語のまま放置）
✅ 「本手法はサンプル効率が高い。つまり、同じ性能に到達するまでに必要な試行回数が少ない。たとえば従来法が10万エピソード必要だった課題を、1万エピソードで解ける」

1文を短く保つ。1文に複数の主張を詰め込まない。読点で繋ぎ続けない。

**過去に読み手が引っかかった語と、その言い換え方**は [phrasing.md](phrasing.md) に蓄積してある。原則3〜5・原則7 の対象語を書くときに引く。

### 原則4：英語用語の扱い

英語の専門用語は無理に日本語化せず、英語のまま記述する。初出時には日本語訳または短い説明を必ず併記する：

> body schema（身体図式：自分の身体の空間的配置を脳が内部表現として保持する仕組み）

略語は初出時に必ず展開：

> VLA model（Vision-Language-Action model：視覚・言語・行動の3モダリティを統合するモデル）

### 原則5：合成語の分解

専門用語の多くは「A＋B」の合成語である（例：報酬モデル、行動クローニング、世界モデル、拡散方策）。**合成語を、構成要素から意味が自明であるかのように使ってはならない**。読み手が A と B を個別に知っていても、「AB」が何を意味するかは合成しただけでは立ち上がらない。

初出時に次の3点を書く：

1. **A がこの文脈で何を指すか**
2. **B がこの文脈で何を指すか**
3. **合成した全体が何を意味するか**（多くの場合、A＋B の単純な和を超える意味を持つ）

❌ **悪い例**（合成語を既知語として扱う）：
> このアプリは systemd で常駐させる。

✅ **良い例**（分解してから使う）：
> このアプリは systemd（システムディー）で常駐させる。`system` は OS 全体、`d` は daemon（デーモン＝画面を持たず裏で動き続けるプロセス）の頭文字で、合わせて「OS の常駐プロセスたちを面倒みる仕組み」を指す。つまり「`python app.py` を手で叩いて動かし続ける」代わりに、起動・再起動・ログの集約を OS 側に任せるということ。

#### 合成語かどうかの判定

迷ったら次を自問する：**「不慣れな読者が、構成要素の意味だけからこの語の指す仕組みを再構成できるか？」** できないなら分解が必要。その分野の教科書の索引に載るレベルの術語は、原則として分解対象とみなす。

### 原則6：コード解説の粒度

コードブロックを示すだけでは解説にならない。各ブロックについて **「何を」「なぜ」「裏で何が起きるか」** の3点をセットで書く。

#### 必須要素

1. **ブロック分割と番号付け**：1〜数行ごとにコメントで番号を振り、コードの後に「ブロック①は〇〇」と各番号を順に解説する。

2. **「何を」と「なぜ」のセット**：
   - 「何を」だけだとリファレンスと変わらない
   - 「なぜ」だけだと再現できない
   - 両方を必ずセットで書く

3. **裏で動いていること**：関数呼び出し1行で複数のステップが走る場合、その流れを時系列で書く。

4. **ローカルとリモートの区別**：「これはローカルPC上で動く」「これはクラウドのコンテナ内で動く」を明示。ユーザーが物理的な位置関係をイメージできるように。

5. **設計判断の理由付け**：「ハードコードせず引数経由にする」と書いたら、必ず「なぜか」も書く。

#### 反パターン

❌ 「ポイント：argparse を使う、SM_MODEL_DIR を参照する、torch.save を呼ぶ」
✅ 「ブロック① で argparse を使うのは、SageMaker が学習時に CLI 引数としてハイパーパラメータを渡してくる仕組みだから。launch.py 側で hyperparameters={...} と書くと、SDK がそれを `--epochs 20` の形に変換して train.py を起動する。だから argparse の受け口を用意する必要がある。」

### 原則7：ユーザー前提の能動的抽出

読者は **自分がすでに知っていること** を再説明されることを嫌う。同時に **自分が知らないと自覚している抽象用語** は概念から欲しがる。このバランスを取るには、ユーザーの直前メッセージから前提を抽出する作業が必要。

#### 抽出すべき信号

- **既知の前提**：ユーザーが何気なく使う用語（「Dockerはデフォで使う」「EC2のUbuntu」など）
  → これらの説明をしない、これと矛盾する表現を避ける
- **未知の用語**：「〇〇というのが分からない」「△△ってどういう意味？」
  → 概念から、それも遠めから説明する
- **明示的な前提除外**：「〇〇は不要」「AWSの基本は知っている」
  → そのまま尊重する

#### 抽象用語が出てきた時のチェックリスト

抽象的な英語ベースの動詞・名詞（「デプロイする」「ホストする」「API化する」など）を書こうとした瞬間、次を確認：

1. ユーザーがこの用語を以前のメッセージで使っているか？
2. 使っていない場合、これは「概念から説明すべき抽象用語」か？
3. もし 2 が Yes なら、用語を使う前に **1-2行の概念説明** を入れる。

例：「学習結果を HTTP API として公開」と書く前に：「ここで言う『HTTP API として公開』とは、別のシステムから HTTP リクエストで推論結果を取得できる、常設のサーバを立てることを指す」と説明する。

### 原則8：出力形式

すべて Markdown で書く。どの md レンダラでも崩れないように：
- 見出しは `#` `##` `###`
- リストは `-`
- コードは ``` で囲む
- 数式は LaTeX `$...$` / `$$...$$`
- HTML 図は **mdに埋め込まず、独立した .html ファイルとして作成する**（詳細は `explainer-structure` 参照）

### 原則9：指摘・質問を受けたときの手続き

読み手からの質問・指摘は、**文書の欠陥の報告**である。感想ではないので、次の3段階で処理する。

#### 段階1：認識合わせ（対応より先）

指摘の意図を自分の言葉で言い換えてから対応に入る。ただし毎回止まって確認すると往復が倍になるので、既定は止まらない：

- **既定（止まらない）**：応答の冒頭1〜2行で「このご指摘を〜という意味に取りました」と解釈を宣言し、そのまま対応に進む。ずれていれば読み手が止められる。
- **例外（止まる）**：指摘の対象箇所が一意に決まらない場合（「分かりにくい」「なぜこうなっている？」など）は、対応に入る前に確認して返答を待つ。

**宣言には2つを含める。** (a) 指摘をどう取ったか、(b) **それを踏まえて次に何をするか**（回答だけで済むのか、どのファイルのどこが壊れていると見ているのか）。(a) だけだと診断のずれが露呈しない — 指摘そのものは正しく引用できていたのに、それを「追記の依頼」と取り違えて往復が増えた例がある（RARM 2026-08-26「溶かし込む」）。

1つのメッセージに複数の疑問が混ざるのが普通である（実データで平均1.9件、最大10件）。**分解して番号を振ること自体を認識合わせに使う。**

#### 段階2：本文の書き直し（追記ではない）

**質問が生じたこと自体が、本文の流れが失敗している証拠**である。だから直すべきは回答の置き場所ではなく、本文そのもの。

- ❌ 質問文を見出しにして、その下に回答を追記する
- ❌ 該当箇所の後ろに「補足」「注」として回答を足す
- ✅ **その疑問が浮かばない流れになるよう、該当する節を書き直す**

書き直しの前に、**何が読み手を引っかからせたのかを言語化する**。特定せずに書き直すと同じ穴が残る。

まず原則1（前提の補完）・原則2（論理の接続）・原則3〜5（言い換えと分解）の未達を疑う。ただし **既存の原則に無理に当てはめない**。どの原則にも該当しないなら、それは「まだ原則になっていない問題」なので、無理に当てはめず、自分の言葉で言語化してから書き直す。

**書き直したあと、回答の形が残っていないかを見る。** 節を書き直しても、次の3つの形は回答文の痕跡として残りやすく、読み手にはそれと分かる（π₀ 2026-09-12：「回答が質問に答える文章を挿入する形の文章の典型的な形」）。

- ❌ **誤読を打ち消す否定形**：「〜であり、『〜が入っている』のでも『〜になる』のでもない」→ 肯定形1文で「何であるか」だけを書く
- ❌ **質問を言い換えた見出し・リード文**：「### X が行っていること」「ここで押さえておきたいのは」「〜が具体的に何を指すか」→ 対象の名前を見出しにし、地の文で述べる
- ❌ **回答であることを示す強調**：読み手が尋ねた一点だけを太字にする → その語の動作の記述から書き始める

3つに共通するのは、**読み手が尋ねたという事実が文の形に残っている**こと。尋ねられなかった場合にも同じ文を書くか、で判定する。

例外：読み手が「本文とは別に説明が欲しい」と明示した場合のみ、別の場所に書く。

#### 記録と、この Skill の改訂（文章改善ループ）

読み手が止まった経験は、この Skill を改訂する材料になる。その記録と改訂は、非公開リポジトリ `~/dev-management-private/writing-loop/` の手順で行う（非公開なので、無い環境もある）。

- **記録**：ユーザーが「記録して」と指示したときだけ行う。エージェントから記録を提案しない。指示を受けたら `~/dev-management-private/writing-loop/README.md` を読み、その手順で `records/` に下書きを作る。どのプロジェクトの会話で指示されても、記録は `dev-management-private` に置いてそのリポジトリにコミットし、作業中のプロジェクトのリポジトリには入れない
- **改訂（ルール化）**：ユーザーが任意のタイミングで始める。記録の件数などを理由に、エージェントから始めたり提案したりしない。始まったら、同じ README の手順に従う
- `~/dev-management-private/` が無い環境では、記録できないことをユーザーに伝える

## 出力前セルフチェック（必須手続き）

**本文を書き終えたら、出力する前に次のチェックリストを応答にコピーし、1項目ずつ潰す。** 1つでも不合格があれば修正してから出す。この手続きは省略不可。長い文書の場合はセクション単位で実施してよい。

```
文章スタイル チェック:
- [ ] 用語：専門用語を上から順に拾い、初出時に定義または言い換えがあるか。合成語（原則5）は分解されているか
- [ ] 文：各文について「この文は何を主張しているか」を一言で言えるか。言えない文（複数主張の詰め込み、係り受けが曖昧）は分割・書き直し
- [ ] 接続：各セクション冒頭・各段落冒頭に、前の内容とのつながりを示す語（だから／しかし／これを踏まえて）または目的の明示があるか
- [ ] 到達基準：文書内の任意の用語・任意の文の意味を問われたとき、文書内の記述だけで答えられるか
- [ ] 検証マーク：一次資料で確認していない記述に「⚠️ 要検証」が付いているか（explainer-citation）
- [ ] 指摘対応（改訂時のみ）：解釈の宣言が冒頭にあるか。回答の追記ではなく本文の書き直しになっているか。回答の形をした文（誤読を打ち消す否定形／質問を言い換えた見出し・リード文／回答であることを示す強調）が残っていないか
```

到達基準で答えられない箇所があれば、前提補完（原則1）か定義追加（原則3〜5）で埋める。

## 禁止事項

- **拡大解釈をしない**：一次情報の主張を超えた一般化、独自解釈の混入をしない
- **断片的な単語列で済ませない**：用語の並列で説明したつもりにならない
- **合成語を未定義のまま使わない**：原則5に従い、初出時に分解する
- **読み手の個人事情に踏み込まない**：「あなたの業務にとっての含意」「あなたの言葉での言い換え」のような、読み手の内部状態に依存する内容は書かない
- **必要以上に長くしない**：1セクションは必要な情報量で済ませる
- **コードを要点列挙だけで済ませない**：原則6に従い、ブロックごとに「何を」「なぜ」「裏で何が起きるか」をセットで書く
- **質問への回答を見出しとして追記しない**：原則9に従い、本文を書き直す
- **回答の形をした文を本文に残さない**：誤読を打ち消す否定形、質問を言い換えた見出し・リード文、回答であることを示す強調（原則9段階2）
- **末尾に「想定される追加質問」を付けない**
- **セルフチェックを飛ばさない**：出力前セルフチェックは必須手続き
