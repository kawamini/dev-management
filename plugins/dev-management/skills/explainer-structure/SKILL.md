# Explainer Structure

ドキュメントの **「どう配置するか」「どう分割するか」「図をどう出すか」** を定義する Skill。
文章スタイルは `explainer-style`、出典は `explainer-citation` が定義する。

ここで作るのは、**仕事で手を動かす前に読む「開発知識のインプット」用のドキュメント**である。読者は事前学習として .md を読み、実務で「全くわからない」を回避する。

## 原則1：粒度を書き始める前に決める

トピックの性質で **詳細型** と **俯瞰型** を使い分ける。ドキュメント冒頭に `> 本ドキュメントは○○型で書きます` の1行を置いて宣言する。ユーザーが「俯瞰で」「詳しく」などのヒントを出したらそれに従う。**迷ったら詳細型。**

| 型 | 対象 | 通読の目安 | 章立て |
|---|---|---|---|
| **詳細型** | 基礎かつ長く使い続ける技術（Git、Linux／シェル、Docker、Python の環境管理、テスト、ログ、デバッグ、HTTP／REST など） | 2〜3時間 | 概念モデル → 頻出操作 → 実務ワークフロー → つまずきポイント → 発展・関連 |
| **俯瞰型** | 応用・特化・移り変わりの早い技術（ROS2 の特定機能、VLA の実装パターン、特定ライブラリの概要など） | 30分 | 全体像 → 必ず押さえる要素3〜5個 → 頻出パターン → つまずきポイント → 次に読むもの |

**つまずきポイントは、どちらの型でも独立した1セクションを置く。** 初学者が引っかかる具体的なエラー・誤解・命名の混乱を列挙する。

## 原則2：1トピック＝1ファイル

ドキュメントは**独立完結**を原則とする。カリキュラム的に連結しない。

- **分割しないのが既定。** 詳細型で長くなっても、まず1ファイルに収める
- 独立したトピックが明らかに2つ以上あるときだけ分け、**多くても3ファイル**。3つに収まらないなら、ファイルを増やさずに扱う範囲を絞り、絞ったことと残した論点を1行で示す
- 複数ファイルになったら、**先頭ファイルの冒頭**に各ファイルの中身と読む順を数行で書く（別立ての目次ファイルは作らない）
- **構成の合意は待たない。** 書き始める前に「詳細型・1ファイルで出します」のように1行で宣言し、そのまま書く
- 末尾に **関連ドキュメント** を1〜3件、関連の性質を一行添えて挙げる
  例：`Docker — コンテナの概念を先に押さえると、Python の環境管理の位置付けが明確になる`

## 原則3：ドキュメント先頭のテンプレ

```markdown
# <トピック名>

> 本ドキュメントは○○型で書きます

**対象**: 何を扱い、何を扱わないか（1〜2行）
**対応する一次情報**: [公式ドキュメントの章名](URL)
**最終確認日**: YYYY-MM-DD

---

（本文）
```

章立ては Markdown 見出し（`##`、`###`）。長い箇条書きより、表と短い段落を優先する。

## 原則4：概念図は独立した HTML ファイルにする

抽象的な構造（システム構成、データの流れ、概念の階層、対比軸、時系列、状態遷移など）を扱うときは概念図を作る。形式は **HTML/CSS の独立した .html ファイル**に固定する。閲覧環境で分岐させない。

**HTML 図を md に埋め込まない。** 多くの md レンダラでは、md 内に書かれた完全な HTML が生コードとして表示されてしまう。

図を作ったら、**本文中で必ず引用する**。「図を作っただけ」で本文から参照がない状態にしない。

```markdown
... の関係を **図1** に示す。

> 図1 は別ファイル：[`git-basics-fig1-object-graph.html`](./git-basics-fig1-object-graph.html)
```

## 原則5：ファイル名の規約

**英小文字とハイフン**で付ける。通し番号や連番は使わない。

| 用途 | パターン |
|---|---|
| 本文 | `<topic>.md`（`git-basics.md`、`docker-overview.md`） |
| 概念図（HTML） | `<本文のファイル名基幹>-fig<N>-<topic>.html`（`git-basics-fig1-object-graph.html`）。本文では `図1` と呼ぶ |
| 作業途中・破棄予定 | `_draft_<topic>.md` |

図のファイル名が `fig1.html` だけだと、**図ファイル単体を見たときにどのドキュメントのものか分からず、つながりが辿れない**。だから本文のファイル名基幹を先頭に置く。

図のために下位ディレクトリ（`figures/` 等）は作らない。ファイル名が所属を示しているので、階層を足しても情報が増えず、参照パスが長くなるだけ。

**避ける命名**：`_v2`、`_supplement`、`_aligned` のような差分を示すサフィックス。ファイル名は最終形を示す。

## 原則6：既存ファイルを継承するときは再検証する

過去に作ったドキュメントを下敷きにする場合、その中身を盲信せず、一次情報と照合し直す（`explainer-citation`）。**誤情報を継承しない。** 特に、移り変わりの早い技術（ライブラリの API、CLI のオプション）は前回の記述が古くなっている前提で見る。

## 出力前セルフチェック（必須手続き）

**① 着手前**（1文字でも書く前に）

```
構造 着手前チェック:
- [ ] 粒度：詳細型／俯瞰型を決め、冒頭に宣言の1行を置いたか
- [ ] ファイル数：1ファイルで収まるか。分けるなら3つ以内か
```

**② ファイルを1つ出力するたび**

```
構造 出力チェック:
- [ ] 図の形式：HTML 図が md に直書きされていないか
- [ ] 図の引用と番号：作った図がすべて本文中で引用されているか。番号が対応しているか（`git-basics-fig1-*.html` ↔ 図1）
- [ ] 命名：英小文字とハイフンか。図が本文のファイル名に紐づいているか。差分サフィックスを使っていないか
```

**③ 完結時**

```
構造 完結チェック:
- [ ] つまずきポイント：独立した1セクションがあるか
- [ ] 関連ドキュメント：末尾に1〜3件、関連の性質を添えてあるか
- [ ] 複数ファイル：先頭ファイルの冒頭に、各ファイルの中身と読む順があるか
```

## 禁止事項

- **粒度を宣言せずに書き始める**（原則1）
- **4ファイル以上に分ける**（範囲を絞る方で対応する）
- **HTML 図を md に直書きする**（md レンダラで生コード表示される）
- **図のために下位ディレクトリを作る**
- **所属の分からない図ファイル名を使う**（`fig1.html` 単体は不可）
- **差分サフィックス（`_v2`、`_supplement`）でファイル名を作る**
- **既存ファイルを盲信して継承する**（誤情報を継ぎ足す）
- **セルフチェックを飛ばす**（必須手続き）
