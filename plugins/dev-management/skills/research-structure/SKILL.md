# Research Structure

研究解説の **「構造設計」** を定義する Skill。
文章スタイルは `research-explainer-style`、出典は `research-citation` に分離されている。
本Skillは「どう配置するか」「どう分割するか」「どんなテンプレートを使うか」を扱う。

## なぜこのSkillが必要か

研究解説は **単一文書ではなく、ナビゲーション可能な構造体** として設計するべき場合が多い。
- 公式ドキュメント体系を踏まえる解説
- 複数トピックを統合した実装ガイド
- コードと概念図を含む大規模な技術解説

これらを 1ファイルに詰め込むと「ページを前後するのが大変」になる。事前に構造を設計することで、読み手のナビゲーションが格段に楽になる。

**デフォルトは分割**。単一の巨大ファイルは例外であり、単一ファイルにする場合はその判断理由を明示する。

ただし分割は「理解を作る」ためのものであって、「後から要点を振り返る」用途は満たさない。この2つは別の層なので、多ファイル構成では要点まとめ（原則7）を必ず併せて作る。

## コア原則

### 原則1：分割判定は書き始める前に行う（最重要）

ファイルを1文字でも書く前に、次の判定手続きを実行する。判定材料はすべて **計画時点で分かるもの** に限る（「書いてみたら長くなった」で判断しない）。

#### 分割判定手続き

以下のいずれか1つでも該当したら **多ファイル構成** にする：

1. 計画時点で `##` 見出しが **7個以上** になる見込み
2. 独立したトピック（例：環境構築 / 学習 / 推論 / データ準備）を **2つ以上** 含む
3. 概念図を **2枚以上** 含む見込み（figures/ ディレクトリが必要になるため）
4. 全体を書き切るのに **複数ターンにまたがる** 見込み
5. 公式ドキュメントの複数の上位章に対応する内容を扱う

**どれにも該当しない、かつ迷いもない場合のみ単一ファイル**。迷ったら分割。

#### 単一ファイルでよい場合

- KBノート形式の単票（`Ref: KB-XXXX` 付きの論文サマリ・用語解説・手順メモ）
- 単一トピックで `##` 見出しが6個以下に収まる短い解説
- 1ターンで書き切れる分量

#### 判定結果の明示

判定結果は本文を書く前にユーザーに示す。多ファイルなら全体マップ（原則2）で、単一ファイルなら「単一ファイルで出します（理由：単一トピックで見出し◯個の見込み）」の1行でよい。**無言で単一巨大ファイルを出すことを禁止する。**

### 原則2：構造設計の事前ステップ

多ファイル構成と判定したら、**全体マップを最初に出して合意を取る**。詳細ファイルは合意後に作る。

#### 事前ステップの順序

1. **公式ガイドの章構造の確認**
   - 解説対象が公式ドキュメントを持つ場合、その章構造を先に確認する（詳細は `research-citation` 原則1）
   - 確認できない場合は推定せず、ユーザーに尋ねる

2. **全体マップを最初に作る**
   - `00_MAP.md` 相当のファイルを最初に出す
   - 公式ガイドの上位2階層
   - 本ガイドのファイル一覧と各ファイルの公式章への対応
   - ユーザーの具体的目的に対する推奨読了順序
   - これでユーザーに構造の合意を取る

3. **合意後に詳細ファイルを順次作成**
   - **1回の応答で出すのは1〜2ファイルまで**。全ファイルを1応答に詰め込まない
   - 「先に書き始めて後で整理」は避ける

4. **最後に要点まとめを作る**
   - 全ファイルが揃った時点で `99_summary.md` を作る（原則7）

5. **過去ファイルの継承時は再検証**
   - 既存の作業ファイルを元にする場合、その中身を盲信せず、公式ドキュメントと照合する
   - 誤情報を継承しない

### 原則3：概念図の独立ファイル化

抽象的な構造（システム構成、データの流れ、概念の階層関係、対比軸、時系列、状態遷移など）が含まれる場合、HTML/CSS で概念図を生成する。

#### 重要ルール：mdに埋め込まない

**HTML/CSS の図は md ファイルに埋め込まず、独立した .html ファイルとして作成する**。
多くの md レンダラ（Notion、Obsidian、GitHub など）では、md 内に書かれた完全な HTML が生コードとして表示されてしまうため。

#### HTML 生成ルール

- スタンドアロン HTML（外部依存なし、すべて1ファイル内に完結）
- CSSは `<style>` タグ内、JavaScript は基本不要
- 配色：背景白・線黒・強調色1〜2色、印刷・スクショ後の可読性優先
- 横幅 800〜1100px を目安
- **図の上部にキャプションとして図番号と所属mdファイル名を書く**（例：`図03-1 ／ 03_bayesian_model_reduction.md`）。図だけをスクショして貼ったときに、出所が追える状態にするため

#### 例外

複雑な階層構造の表現には Mermaid 記法も検討するが、Notion 等で表示されない場合がある。デフォルトは HTML/CSS 独立ファイル。

### 原則4：ファイル名の規約

| 用途 | パターン |
|---|---|
| 単発の解説 | `<topic>.md`（例：`sagemaker_overview.md`） |
| 多ファイルガイドの一部 | `<NN>_<topic>.md`（連番つき、例：`05_model_training.md`） |
| 全体マップ | `00_MAP.md` |
| 要点まとめ | `99_summary.md` |
| 概念図 | `<所属md番号>_fig<N>_<topic>.html`（`figures/` 配下） |
| 作業途中・破棄予定 | `_draft_<topic>.md` |

#### 図の命名が所属mdに縛られる理由

図のファイル名が `fig_<topic>.html` だけだと、**図ファイル単体を見たときにどの解説に属するのか分からず、ファイル間のつながりが辿れない**。だから所属する md の連番を先頭に置く。

- `03_fig1_bmr_flow.html` = `03_*.md` の1枚目の図
- 本文中の呼び方は **`図03-1`**（`図1` のような通し番号は使わない）

単発解説（連番のない `<topic>.md`）に図を付ける場合は、md のファイル名基幹をそのまま使う（`sagemaker_overview_fig1_flow.html`、本文では `図1`）。

**避けるべき命名**：`_v2`、`_supplement`、`_aligned` など差分を示すサフィックス。差分管理は git に任せて、ファイル名は最終形を示す。

### 原則5：全体マップ（00_MAP.md）の構成

多ファイル成果物の入口となるマップファイルには、以下を含める：

1. **目的の明示**：このガイドが何を扱い、何を扱わないか
2. **公式ガイドの章構造**：上位2階層程度をディレクトリツリー形式で
3. **本ガイドのファイル構成**：ファイル一覧と各ファイルの公式章への対応（`99_summary.md` も含める）
4. **推奨読了順序**：ユーザーの目的別の読み順
5. **過去ファイルの位置づけ**：既存の作業ファイルがある場合、どれが現役でどれが履歴か明示

### 原則6：解説本文中での図の引用

図を生成したら、本文中で必ず引用する：

```markdown
... の関係を **図03-1** に示す。

> 図03-1 は別ファイル：[`03_fig1_bmr_flow.html`](./figures/03_fig1_bmr_flow.html)
```

「図を作っただけ」で本文中の引用がない状態は避ける。

### 原則7：要点まとめ（99_summary.md）

分割された解説群は理解を **作る** ための資料であり、後から要点を **振り返る** 用途には向かない。この層を埋めるのが要点まとめ。多ファイル構成では必須、単一ファイルの解説では不要。

#### 構成：1つの要点セットから2つの見え方

1ファイルの中に、同じ番号で対応する2つのセクションを置く。

```markdown
# 99_summary — <ガイド名> 要点まとめ

**使い方**: 前半の問いに自分で答えてから、後半で答え合わせをする。時間がないときは後半だけ読む。
**対象ファイル**: 01〜NN

---

## 問い

1. （問い）… → `03`
2. （問い）… → `05`
...

---

## 要点

1. （上の問い1に対する要点。3〜6行）
2. （上の問い2に対する要点）
...
```

#### 作り方のルール

- **問いと要点は同じ要点セットから作る**。番号が1対1で対応していること
- 問いは「〇〇とは何か」で終わらせず、**その解説の核心を突く形**にする（「BMR が素朴な再学習より速いのは、何を計算せずに済ませているからか」）
- 各問いに、根拠となるファイルの連番を付ける（読み返す先が分かるように）
- 要点は1項目 3〜6行。ここで新しい説明を始めない（詳細は本体ファイルの役割）
- 項目数は **7〜12個** を目安にする。それ以上必要なら、ガイドの分割単位そのものを見直す

#### Notion に取り込むとき

「## 要点」の見出しをトグル見出しに変換すると、問いに答えるまで答えを隠せる。ファイル側は通常の見出しのままでよい。

## 対象に応じた構造選択（テンプレート集）

### 論文の場合（KBノート形式・単一ファイル）

```markdown
**Ref**: KB-XXXX

# [論文タイトル]

**主な出典**: [著者], [venue], [年] ([URL])

## 前提となる文脈
[必要に応じて、2〜4行で]

## 1行サマリ

## この論文が解こうとしている問題
[先行研究の何が足りなかったか]

## 仮説

## 検証の方法
[仮説をどう確かめようとしたか、設計の論理]

## 実験方法

## 結果

## 考察
[結果が仮説をどう支持/否定するか、限界、含意]

## 未解消の疑問
[読み終わってもまだ分からない点]
```

**注意**：これは KB 単票用。論文を精読するための **閲読ガイド** を作る場合は、多ファイル解説（後述）として設計する（背景・動機 → 概念枠組み → 手法 → 実験、の連番ファイル構成）。

### 用語・概念の場合（単一ファイル）

```markdown
**Ref**: KB-XXXX

# [用語名]（[英語表記]）

## 前提となる文脈
[必要に応じて]

## 1行定義

## この概念が解こうとしている問題

## 詳しい説明
[平易な言い換え、メカニズム]

## 具体例
[少なくとも1つ、できれば2〜3]

## 関連概念・対比される概念
- [類似概念との違い]
- [混同しやすい概念との区別]
```

### 技術・手順の場合（短〜中規模、単一ファイル）

```markdown
**Ref**: KB-XXXX

# [トピック]

## 前提となる文脈

## 何のためのものか

## 仕組みの概要

## 具体的な使い方
[コード例を含む場合は、実行確認の有無を明記]

## 注意点・落とし穴
```

### 多ファイル解説の場合（論文閲読ガイド・公式ドキュメント体系の解説など）

```
<guide_name>/
├── 00_MAP.md                ← 全体マップ（必須）
├── 01_<topic>.md            ← 章順に連番
│                               （未知の分野なら 01 は背景・動機に充てる）
├── 02_<topic>.md
├── ...
├── NN_pitfalls.md           ← 注意点・落とし穴
├── 99_summary.md            ← 要点まとめ（必須・最後に作る）
└── figures/
    ├── 03_fig1_<topic>.html ← 概念図は所属md番号つきの独立HTMLで
    └── ...
```

各 md ファイルの先頭テンプレ：

```markdown
# NN_<topic>

**目的**: このファイルが扱う範囲を1〜2行で
**公式の対応章**: [章名](URL)
**最終確認日**: YYYY-MM-DD

---

（本文）
```

## 出力前セルフチェック（必須手続き）

ファイルを出力する前に、次の6項目を順に検査する。1つでも不合格があれば修正してから出す。

1. **分割判定の実施**：原則1の判定手続きを実行し、結果をユーザーに明示したか
2. **マップの存在**：多ファイル構成なら `00_MAP.md` が先頭にあるか（合意済みか）
3. **要点まとめの存在**：多ファイル構成が完結したなら `99_summary.md` があるか。問いと要点の番号が1対1で対応しているか
4. **図の分離**：HTML図が md に直書きされていないか（すべて `figures/` 配下の独立HTMLか）
5. **図の引用と番号**：生成した図がすべて本文中で引用されているか。ファイル名と本文の図番号が所属md連番で揃っているか（`03_fig1_*.html` ↔ `図03-1`）
6. **命名規約**：連番・差分サフィックス禁止に従っているか

## 禁止事項

- **分割判定なしで単一巨大ファイルを出す**（原則1の手続きを省略しない）
- **1回の応答に全ファイルを詰め込む**（1応答1〜2ファイルで順次出す）
- **HTML図を md に直書き** する（mdレンダラで生コード表示される）
- **全体マップなしで多ファイル成果物を作る**（ユーザーがナビゲートできない）
- **要点まとめなしで多ファイル成果物を完結させる**（振り返る手段がなくなる）
- **所属mdの分からない図ファイル名を使う**（`fig_<topic>.html` 単体は不可）
- **過去ファイルを盲信して継承する**（誤情報を継ぎ足す）
- **差分サフィックス（`_v2`, `_supplement`）でファイル名を作る**
- **末尾に「想定される追加質問」を付けない**（運用で参照されていないため廃止した）

## このSkillの改訂方針

このSkillは運用の中で改訂される前提で書かれている。改訂の兆候：

- ユーザーが「ナビゲートしにくい」「前後を行き来するのが大変」と指摘した
- 単一ファイルで出したものが後から分割になった（原則1の判定基準の閾値がずれている）
- 図がレンダリングされなかった／どの解説の図か分からなくなった
- 過去ファイルの誤情報を継承して指摘された
- ファイル名の散乱で何が現役か分からなくなった

これらが見えたら、対応する原則を具体化する。改訂は思いつきで行わず、**指摘ログに溜まった記録を根拠にする**（ルール化の条件は同種3回以上）。
