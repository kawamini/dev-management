# Research Structure

研究解説の **「構造設計」** を定義する Skill。
文章スタイルは `research-explainer-style`、出典は `research-citation` に分離されている。
本Skillは「どう配置するか」「どう分割するか」「どんなテンプレートを使うか」を扱う。

## なぜこのSkillが必要か

解説は、読み手が前後を行き来せずに読めることが大事である。ファイルを細かく分けすぎると、どこに何が書いてあるかを追うだけで疲れる。逆に、公式ドキュメント体系を踏まえる解説や、論文1本を精読するガイドのように大きなものは、構造を先に設計しないと読み手がナビゲートできない。このSkillは、その2つの間で形を決める。

## コア原則

### 原則1：ファイルの数は書き始める前に決める（最重要）

ファイルを1文字でも書く前に、ファイルの数を決める。判定材料はすべて **計画時点で分かるもの** に限る（「書いてみたら長くなった」で判断しない）。

- **既定は1ファイル。** ファイルを作らない回答（チャットでの回答）なら、チャットの中で完結させる。長くなっても、まず1ファイルに収める
- 独立したトピック（例：環境構築 / 学習 / 推論）が明らかに2つ以上あるときだけ分け、**多くても3ファイル**。3つに収まらないなら、ファイルを増やさずに扱う範囲を絞り、絞ったことと残した論点を1行で示す
- 2〜3ファイルに分けたときは、**先頭ファイルの冒頭**に各ファイルの中身と読む順を数行で書く。別立ての目次ファイルは作らない
- **例外**：プロジェクトの指示（`CLAUDE.md` など）が多ファイル構成を決めているとき（例：論文閲読ガイド）は、その指示に従い、下の「多ファイル解説」の構成（`00_MAP.md`〜`99_summary.md`）を使う。この Skill の側から多ファイル構成を選ばない

#### 判定結果の明示

決めた形は、本文を書く前に1行で示す（「1ファイルで出します」「2ファイルに分けます（理由：環境構築と学習の2トピック）」）。**無言でファイルを分けない。**

### 原則2：多ファイル解説の事前ステップ

ここから原則7までの `00_MAP.md`・`99_summary.md`・図の命名などは、**多ファイル解説**（原則1の例外として、プロジェクトの指示が多ファイル構成を決めたもの）の規則である。2〜3ファイルに分けただけの解説には、図の規則（原則3・4・6）だけを使う。

多ファイル解説では、**全体マップを最初に出して合意を取る**。詳細ファイルは合意後に作る（プロジェクトの指示が合意を待たないと決めていれば、それに従う）。

#### 事前ステップの順序

1. **公式ガイドの章構造の確認**
   - 解説対象が公式ドキュメントを持つ場合、その章構造を先に確認する（詳細は `research-citation` 原則1）
   - 確認できない場合は推定せず、ユーザーに尋ねる

2. **全体マップを最初に作る**
   - `00_MAP.md` 相当のファイルを最初に出す
   - 公式ガイドの上位2階層
   - 本ガイドのファイル一覧と各ファイルの公式章への対応
   - ユーザーの具体的目的に対する推奨読了順序
   - これでユーザーに構造の合意を取る

3. **合意後に詳細ファイルを順次作成**
   - **1回の応答で出すのは1〜2ファイルまで**。全ファイルを1応答に詰め込まない
   - 「先に書き始めて後で整理」は避ける

4. **最後に全体像を作る**
   - 全ファイルが揃った時点で `99_summary.html` と `99_summary.md` を作る（原則7）

5. **過去ファイルの継承時は再検証**
   - 既存の作業ファイルを元にする場合、その中身を盲信せず、公式ドキュメントと照合する
   - 誤情報を継承しない

### 原則3：概念図の独立ファイル化

抽象的な構造（システム構成、データの流れ、概念の階層関係、対比軸、時系列、状態遷移など）が含まれる場合、HTML/CSS で概念図を生成する。

#### 重要ルール：mdに埋め込まない

**HTML/CSS の図は md ファイルに埋め込まず、独立した .html ファイルとして作成する**。
多くの md レンダラ（Notion、Obsidian、GitHub など）では、md 内に書かれた完全な HTML が生コードとして表示されてしまうため。

#### HTML 生成ルール

- スタンドアロン HTML（外部依存なし、すべて1ファイル内に完結）
- CSSは `<style>` タグ内、JavaScript は基本不要
- 配色：背景白・線黒・強調色1〜2色、印刷・スクショ後の可読性優先
- 横幅 800〜1100px を目安
- **図の上部にキャプションとして図番号と所属mdファイル名を書く**（例：`図03-1 ／ 03_bayesian_model_reduction.md`）。図だけをスクショして貼ったときに、出所が追える状態にするため

#### 例外

複雑な階層構造の表現には Mermaid 記法も検討するが、Notion 等で表示されない場合がある。デフォルトは HTML/CSS 独立ファイル。

### 原則4：ファイル名の規約

| 用途 | パターン |
|---|---|
| 単発の解説 | `<topic>.md`（例：`sagemaker_overview.md`） |
| 多ファイルガイドの一部 | `<NN>_<topic>.md`（連番つき、例：`05_model_training.md`） |
| 全体マップ | `00_MAP.md` |
| 全体像（多ファイル解説） | `99_summary.html`（本体）、`99_summary.md`（入口）。原則7 |
| 参照箇所のまとめ（多ファイル解説） | `98_sources.md`（`research-citation` 原則2） |
| 一次資料から切り出した図・表 | `img/fig<N>.png`、`img/table<N>.png`（原文の番号） |
| 概念図 | `<所属md番号>_fig<N>_<topic>.html`（`figures/` 配下） |
| 作業途中・破棄予定 | `_draft_<topic>.md` |

#### 図の命名が所属mdに縛られる理由

図のファイル名が `fig_<topic>.html` だけだと、**図ファイル単体を見たときにどの解説に属するのか分からず、ファイル間のつながりが辿れない**。だから所属する md の連番を先頭に置く。

- `03_fig1_bmr_flow.html` = `03_*.md` の1枚目の図
- 本文中の呼び方は **`図03-1`**（`図1` のような通し番号は使わない）

単発解説（連番のない `<topic>.md`）に図を付ける場合は、md のファイル名基幹をそのまま使う（`sagemaker_overview_fig1_flow.html`、本文では `図1`）。

**避けるべき命名**：`_v2`、`_supplement`、`_aligned` など差分を示すサフィックス。差分管理は git に任せて、ファイル名は最終形を示す。

### 原則5：全体マップ（00_MAP.md）の構成

多ファイル成果物の入口となるマップファイルには、以下を含める：

1. **公式ガイドの章構造**：上位2階層程度をディレクトリツリー形式で
2. **本ガイドのファイル構成**：ファイル一覧と各ファイルの公式章への対応（`99_summary.md` も含める）
3. **推奨読了順序**：ユーザーの目的別の読み順
4. **過去ファイルの位置づけ**：既存の作業ファイルがある場合、どれが現役でどれが履歴か明示

ガイドそのものについての説明（このガイドの目的、扱う範囲・扱わない範囲、レビューの結果や未解決の一覧）は、マップにも各ファイルにも書かない。読み手が内容を理解するのに使わないからである（2026-11-08、閲読ガイドへの指摘による）。

### 原則6：解説本文中での図の引用

図を生成したら、本文中で必ず引用する：

```markdown
... の関係を **図03-1** に示す。

> 図03-1 は別ファイル：[`03_fig1_bmr_flow.html`](./figures/03_fig1_bmr_flow.html)
```

「図を作っただけ」で本文中の引用がない状態は避ける。

md の本文に置く図（Mermaid、画像）には、**図のすぐ下に「図03-1：<題>」の形で題を付ける**。図の上の行に番号を書くと、それが図の題だと読み手に伝わらない（2026-11-08、閲読ガイドへの指摘による）。HTML の独立ファイルは、原則3 のとおりファイルの上部に書く。

#### 一次資料の図と表を載せる

論文などの一次資料に図や表があり、それが理解を助けるなら、該当部分を画像に切り出して載せ、本文で説明する（PDF なら `pdftoppm` で該当ページを画像にして切り出す）。画像はガイドのフォルダの `img/` に置き、原文の番号で名付ける（`img/fig2.png`、`img/table3.png`）。題は「Figure 2（原論文）：<題の訳>」とする。

- 本文で「Figure 2」「Table 3」と番号を出すのは、その図や表を載せて説明するときだけにする。載せないなら番号は本文に出さず、場所は参照箇所のまとめ（`research-citation` 原則2）にだけ書く
- 切り出した図だけでは読み取りにくいとき（読み手が図について質問したときなど）は、説明のための図を Mermaid か HTML で足す

### 原則7：全体像（99_summary.html と 99_summary.md）

01〜NN の解説群は、理解を **作る** ための資料である。量が多いので、後からふと振り返りたくなっても、要点をすぐには掴めない。この層を埋めるのが全体像で、解説の対象（論文や技術）がどういうものかを、**図と短い文で1枚に**まとめる。多ファイル解説では必須、1〜3ファイルの解説では不要。

01〜NN の個々の結果を項目ごとに並べるのではなく、抽象度を1段上げ、項目同士のつながりが見える流れで書く（2026-11-09、閲読ガイドへの指摘による。問いと要点を12組並べた形は、具体的すぎて項目同士のつながりが分からず、全体像が掴めなかった）。

#### 構成：本体の HTML と、入口の md

| ファイル | 役割 | 中身 |
|---|---|---|
| `99_summary.html` | 本体 | 1枚のページ。下の「本体の流れ」の節を上から並べる。原則3 の HTML 生成ルールに従う（独立したファイル、外部依存なし） |
| `99_summary.md` | 入口 | 対象を一言でまとめた2〜4文、本体へのリンクと開き方（ブラウザか、エディタの HTML のプレビュー）、本体の各節と詳しく書いたファイルの対応表 |

入口の md を置くのは、HTML を表示できない md のビューア（Obsidian など）でも、何がどこにあるかを追えるようにするためである。2つとも、ガイドのフォルダの直下に置く。本体は図ではなくページなので、原則4 の図の命名（`figures/`、`<NN>_fig<N>_*.html`）は使わない。

#### 本体の流れ

上から順に、次の節を置く。論文以外（技術や公式ドキュメント）を解説したガイドでは、節の名前を対象に合わせて読み替える。

1. **一言**：対象が何をするものかを、2〜3文で書く
2. **何が問題で、どう解いたか**：背景の問題と、それに対する発想
3. **仕組み**：構成図1枚と、それがどう動くか
4. **なぜ効くか**：仕組みが問題を解く理由。図か、理由ごとに分けた短い文で書く
5. **どれくらい効くか**：中心の数字を3〜5個。何と何を比べた数字かを添える
6. **読むときの注意**：3点前後。注意点・落とし穴のファイル（`NN_pitfalls.md`）から選ぶ
7. **その先**：発展や応用。無ければ省く

#### 作り方のルール

- 01〜NN が揃ってから作る。**新しい説明を始めない**。書くのは 01〜NN に書いたことだけで、数字と主張は本文と突き合わせてから載せる
- 各節の見出しの横に、詳しく書いたファイルの連番（必要なら節）を付ける。読み返す先が分かるようにするため
- 図は少なくとも2枚置く。仕組みの構成図と、なぜ効くかを示す図である。番号は `図99-1` の形で付け、題は図のすぐ下に書く（原則6）
- 各節の文は数文に抑える。それより多く要るなら、その説明は本体のファイルの役割である
- 用語は、01〜NN と同じ呼び方に揃える
- 問いに自分で答えてから答え合わせをする形（問いと要点）は使わない
- 書き終えたら、ブラウザで表示して、文字のはみ出しや図の重なりが無いかを確かめる

## 対象に応じた構造選択（テンプレート集）

### 論文の場合（KBノート形式・単一ファイル）

```markdown
**Ref**: KB-XXXX

# [論文タイトル]

**主な出典**: [著者], [venue], [年] ([URL])

## 前提となる文脈
[必要に応じて、2〜4行で]

## 1行サマリ

## この論文が解こうとしている問題
[先行研究の何が足りなかったか]

## 仮説

## 検証の方法
[仮説をどう確かめようとしたか、設計の論理]

## 実験方法

## 結果

## 考察
[結果が仮説をどう支持/否定するか、限界、含意]

## 未解消の疑問
[読み終わってもまだ分からない点]
```

**注意**：これは KB 単票用。論文を精読するための **閲読ガイド** を作る場合は、多ファイル解説（後述）として設計する（背景・動機 → 概念枠組み → 手法 → 実験、の連番ファイル構成）。

### 用語・概念の場合（単一ファイル）

```markdown
**Ref**: KB-XXXX

# [用語名]（[英語表記]）

## 前提となる文脈
[必要に応じて]

## 1行定義

## この概念が解こうとしている問題

## 詳しい説明
[平易な言い換え、メカニズム]

## 具体例
[少なくとも1つ、できれば2〜3]

## 関連概念・対比される概念
- [類似概念との違い]
- [混同しやすい概念との区別]
```

### 技術・手順の場合（短〜中規模、単一ファイル）

```markdown
**Ref**: KB-XXXX

# [トピック]

## 前提となる文脈

## 何のためのものか

## 仕組みの概要

## 具体的な使い方
[コード例を含む場合は、実行確認の有無を明記]

## 注意点・落とし穴
```

### 多ファイル解説の場合（論文閲読ガイド・公式ドキュメント体系の解説など）

```
<guide_name>/
├── 00_MAP.md                ← 全体マップ（必須）
├── 01_<topic>.md            ← 章順に連番
│                               （未知の分野なら 01 は背景・動機に充てる）
├── 02_<topic>.md
├── ...
├── NN_pitfalls.md           ← 注意点・落とし穴
├── 98_sources.md            ← 参照箇所のまとめ（本文の (ref. n) の場所と原文）
├── 99_summary.md            ← 全体像の入口（必須・最後に作る）
├── 99_summary.html          ← 全体像の本体。図と短い文の1枚（必須・最後に作る）
├── img/
│   └── fig2.png             ← 一次資料から切り出した図・表（原文の番号）
└── figures/
    ├── 03_fig1_<topic>.html ← 概念図は所属md番号つきの独立HTMLで
    └── ...
```

各 md ファイルの先頭テンプレ：

```markdown
# NN_<topic>

**公式の対応章**: [章名](URL)
**最終確認日**: YYYY-MM-DD

---

（本文）
```

## 出力前セルフチェック（必須手続き）

ファイルを出力する前に、次の6項目を順に検査する。1つでも不合格があれば修正してから出す。

1. **ファイルの数**：原則1に従い、1ファイル（分けても3つまで）か。分けたなら理由を明示し、先頭ファイルの冒頭に中身と読む順を書いたか。多ファイル解説なら、プロジェクトの指示がそれを決めているか
2. **マップの存在**：多ファイル解説なら `00_MAP.md` が先頭にあるか（合意済みか）
3. **全体像の存在**：多ファイル解説が完結したなら `99_summary.html` と `99_summary.md` があるか。本体が原則7 の流れに沿い、図が2枚以上あり、各節に詳しく書いたファイルの連番が付いているか
4. **図の分離**：HTML図が md に直書きされていないか（すべて `figures/` 配下の独立HTMLか）
5. **図の引用と番号**：生成した図がすべて本文中で引用されているか。ファイル名と本文の図番号が所属md連番で揃っているか（`03_fig1_*.html` ↔ `図03-1`）
6. **命名規約**：連番・差分サフィックス禁止に従っているか
7. **ガイド自身の説明**：目的・扱う範囲・レビューの結果など、ガイドそのものについての説明を書いていないか（原則5）
8. **図の題と一次資料の図表**：md の図の題が図のすぐ下にあるか。本文で番号を出した一次資料の図や表を、載せて説明しているか（原則6）

## 禁止事項

- **プロジェクトの指示が無いのに4ファイル以上に分ける**（原則1。収まらないなら範囲を絞る）
- **無言でファイルを分ける**（原則1の判定結果の明示を省かない）
- **多ファイル解説で、1回の応答に全ファイルを詰め込む**（1応答1〜2ファイルで順次出す。プロジェクトの指示が止まらずに走り切ると決めていれば、それに従う）
- **HTML図を md に直書き** する（mdレンダラで生コード表示される）
- **全体マップなしで多ファイル解説を作る**（ユーザーがナビゲートできない）
- **全体像なしで多ファイル解説を完結させる**（振り返る手段がなくなる）
- **所属mdの分からない図ファイル名を使う**（`fig_<topic>.html` 単体は不可）
- **過去ファイルを盲信して継承する**（誤情報を継ぎ足す）
- **差分サフィックス（`_v2`, `_supplement`）でファイル名を作る**
- **末尾に「想定される追加質問」を付けない**（運用で参照されていないため廃止した）

## このSkillの改訂方針

このSkillは運用の中で改訂される前提で書かれている。改訂の兆候：

- ユーザーが「ナビゲートしにくい」「前後を行き来するのが大変」と指摘した
- 分けすぎて、どこに何が書いてあるかを追うのが大変になった
- 1ファイルで出したものが、読み手には長すぎて後から分けることになった（原則1の判定がずれている）
- 図がレンダリングされなかった／どの解説の図か分からなくなった
- 過去ファイルの誤情報を継承して指摘された
