# Project Rules — 開発・研究の管理ルール

このルールの目的は2つある。

1. AI が何をしたかを、ユーザーが後から理解できるようにする
2. AI が次の作業を始めるときに、過去の積み重ねのうち何を踏まえるべきかを選べるようにする

2 がうまくいかない主な原因は、目的に対する探究の記録と、途中の実装変更の記録が同じ場所に混ざることである。だから記録を種類ごとに分ける。

## 1. 2つの記録層

| 層 | 何を記録するか | 実体 |
|---|---|---|
| コード層 | 実装がどう変わったか・なぜ変えたか | Git のコミット、`decisions/` |
| ノード層 | 1回の探究ごとの背景・目的・方法・結果・知見と、探究どうしのつながり | `trials/<ID>/<ID>.md`（1ファイル＝1ノード） |

ノードは実行時のコードの版をコミット ID で指す。目的と関係しない実装変更はノードにしない。

## 2. Git

### 2.1 実験を実行する前に必ずコミットする

ノードの実験・検証を実行する直前に、次の2つを行う。

```bash
git status --porcelain      # 何も表示されなければ未コミットの変更はない。表示されたら先にコミットする
git rev-parse --short HEAD  # 表示されたコミット ID を、ノード本体の code_commit に書く
```

未コミットの変更が残ったまま実行すると、どのコードで実行したかが記録から分からなくなり、再現できない。

### 2.2 Git に入れないもの

- `trials/*/outputs/`（ログ、チェックポイント、動画など）
- 学習済み重み（`*.ckpt`、`*.pt`、`*.safetensors`）
- 複数のノードで共有する大きなデータセット（リポジトリの外に置き、ノードの方法節にパスを書く）

ひな形の `.gitignore` にこれらが書いてある。すでに追跡しているファイルは `.gitignore` に書いても追跡され続けるので、`git rm --cached <ファイル>` で追跡を外してから追加する。

### 2.3 コミットの種別

コミットメッセージの先頭に種別と対象を書く（[Conventional Commits 1.0.0](https://www.conventionalcommits.org/en/v1.0.0/) に、ノード記録用の `exp` を足したもの）。

| 種別 | 使う場面 | 例 |
|---|---|---|
| `feat` | 機能の追加 | `feat(train): LoRA の rank を設定ファイルから指定可能にする` |
| `fix` | バグ修正 | `fix(data): 正規化の平均値を学習データから再計算する` |
| `refactor` | 挙動を変えない整理 | `refactor(env): 報酬計算を関数に切り出す` |
| `exp` | `trials/` の追加・更新 | `exp(T004): rank 32 の結果を記録` |
| `docs` | `decisions/`・README などの更新 | `docs(D01): データローダ並列化の判断を記録` |

実装変更と記録の更新は、別のコミットにする。

### 2.4 実装変更の理由を残す場所

- 小さい変更：コミットメッセージの本文に「何のために変えたか」を書く
- 方針に関わる変更（データローダの構成、シミュレータの版の変更など）：`decisions/D<2桁>-<内容>.md` に、状況・決定（コミット ID）・検討した他案・影響を書く。ひな形は `templates/decision.md`

## 3. ノード

### 3.1 ノードの定義

**ノード＝目的を1つ持ち、結果（失敗を含む）が出た探究のまとまり。** 目的が1つならノードも1つにする。

- 学習率を5通り振って最良を探す → ノード1つ（中に5回の実行）
- Isaac Lab を導入して動く構成を見つける → ノード1つ（環境構築では「動く構成を見つける」ことが目的になる）
- 動作確認のための短い試運転 → ノードにしない（目的がない）
- データローダの並列化 → ノードにしない（`decisions/` に書く）

### 3.2 ID・フォルダ・ファイル

```
trials/
├── INDEX.md
└── T004-lora-rank-32/              ← T<3桁の通し番号>-<内容を表す英小文字とハイフン>
    ├── T004-lora-rank-32.md        ← ノード本体。ファイル名はフォルダ名と同じにする
    ├── instructions.md             ← 実装・実行を別の担当に任せるときの指示書（任意）
    ├── report.md                   ← ユーザー向けの解説レポート（explainer 系 Skill に従って書く）
    └── outputs/                    ← 成果物。Git に入れない
```

ノード本体のファイル名をフォルダ名と同じにするのは、Obsidian などの wikilink（`[[ファイル名]]`）がファイル名でノートを指すためである（[Obsidian: Internal links](https://obsidian.md/help/Linking+notes+and+files/Internal+links)）。

### 3.3 ノード本体の書き方

ひな形は `templates/node/T000-slug.md`。先頭の frontmatter に再現情報を、本文に5つの節を書く。

| 節 | 書くこと |
|---|---|
| 背景 | なぜこの探究を始めたか。使った親ノードの結果・知見へのリンクを含む |
| 目的 | 確かめたいこと。1つに絞る |
| 方法 | 何をどう変え、どう測ったか。親ノードの設定・手順を使うならリンクする。再現コマンドを書く |
| 結果 | 観測したこと（数値、動いた／動かなかった）。解釈は書かない |
| 知見 | 結果から言えることと、それが成り立つ範囲 |

結果と知見を分けるのは、後で解釈が誤りだと分かっても結果を使い続けられるようにするためである。知見には必ず成り立つ範囲を書く。

frontmatter の `code_commit`・`config`・`seed`・`env` が再現情報である。この4つで「同じコード・同じ設定・同じ乱数の種・同じ環境」を再現できるように書く。

### 3.4 ノードのつながり（エッジ）

ノードどうしのつながりは、**子ノード（後から始めたノード）の本文に、親ノードへのリンクとして書く**。リンクを置いた節がつながりの意味になる。

| リンクを置く節 | 意味 |
|---|---|
| 背景 | 親の結果・知見があったので、この探究が生まれた |
| 目的 | 親の知見を確かめ直す、または反証する |
| 方法 | 親で決まった設定・手順・データを使う |

親は複数でよい。リンクは常に終わったノードを指すので、つながりが循環することはない。

```markdown
## 背景
- [[T002-lora-rank-16]] の結果：rank 16 で成功率 71%。失敗の多くは把持位置のずれ

## 方法
[[T003-learning-rate-sweep]] で最良だった学習率 1e-4 のまま、rank だけを 32 に変える。
```

別のプロジェクトのノードを親にするときは、wikilink ではなくパスで書く（例：`isaaclab-env/trials/T004-camera-sensor`）。

### 3.5 status

| status | 意味 |
|---|---|
| `running` | 実行中 |
| `valid` | 結果を次のノードの根拠に使ってよい |
| `invalid` | 処理の誤りなどで結果が使えない |
| `abandoned` | 途中で中止した |

### 3.6 誤りが見つかったとき

ノードのフォルダは**移動も削除もしない**。移動すると、子ノードからのリンクが切れるからである。

1. 誤りのあったノードを `status: invalid` にし、本文に何が誤りだったかと、置き換え先のノードへのリンクを書く
2. やり直しは新しいノードにする
3. 誤りのあったノードを親に持つ子ノードを探し、該当する節に「（T005 は invalid。この記述は見直しが必要）」と書き足す

```bash
grep -rl --include="T*.md" "\[\[T005" trials/   # T005 を親に持つノードを一覧する
```

invalid のノードの設定や手順を、誤りを直したうえで方法に使うのは構わない。invalid のノードの**結果・知見**を根拠にしてはいけない。

### 3.7 条件を追加して既存の結果と統合するとき

既存ノードの実行を再実行せずに、新しい条件だけを実行して比較をまとめるときは、新しいノードを作り、frontmatter の `runs` に再利用する実行を書く。

```yaml
runs:
  - {condition: rank16, from: T002, commit: c9e01f2}   # 再利用
  - {condition: rank32, from: T004, commit: d52ff48}   # 再利用
  - {condition: rank64, commit: 9f1e2d3}               # 今回だけ実行
```

再利用してよいのは、評価のコード・設定・環境の版が同じときだけである。再利用する各ノードのコミットと今回のコミットの間で差分を確かめ（例：`git diff d52ff48 9f1e2d3 -- src/eval configs/eval`）、差分が無いか、あっても評価に影響しない理由を方法節に書く。

### 3.8 outputs/ の扱い

- 成果物は各ノードのフォルダの `outputs/` に出す（学習スクリプトの出力先を引数で `trials/<ID>/outputs/` に指定する）
- `invalid`・`abandoned` のノードの `outputs/` は、30日を過ぎたら削除してよい。削除はユーザーの指示があるときに行う
- ノード本体の md は削除しない

## 4. trials/INDEX.md

プロジェクトの入口。作業を始める前に必ず読む。ひな形は `templates/project/trials/INDEX.md`。

- **目標**：プロジェクトとして目指すこと。最初から決まっていなくてよく、1つとは限らない。決まった時点で書き足し、状態（`active` / `achieved` / `dropped`）を付ける
- **末端ノード**：まだ子を持たないノード。次の探究はここから始まる。1行の要約を付ける
- **主な流れ**：ノードのつながりのうち、主要なものを短く書く

ノードの結果が出たら、末端ノードの一覧を更新する。

## 5. 作業の手順

### 新しいノードを始めるとき

1. `trials/INDEX.md` を読む
2. 使う親ノードを選び、その本体を読む。親の背景節から、さらに必要な祖先を辿る
3. 親の status を確かめる（invalid の結果・知見を根拠にしない）
4. 背景・目的・方法を下書きし、ユーザーと目的と方法を合わせる
5. `templates/node/` から新しいフォルダを作る

### 実行するとき

1. 2.1 の実行前コミットを行い、frontmatter の再現情報を埋める
2. status を `running` にする
3. 成果物は `outputs/` に出す

### 結果が出たら

1. 結果と知見の節を書き、status を更新する
2. ユーザー向けの `report.md` を explainer 系 Skill に従って書く
3. `trials/INDEX.md` を更新する
4. ノードの記録を `exp` 種別でコミットする。1回の依頼でまとめて処理したノードは、1つのコミットにまとめる（まとめて取り消せるようにするため）

## 6. 登録と取り消し

ノードの登録にユーザーの承認は要らない。その代わり、ユーザーがいつでも未確認の範囲を見て、取り消せるようにしておく。

```bash
git diff --stat kg-reviewed..HEAD -- 'trials/*/T*.md'   # 前回確認以降に追加・変更されたノード
git tag -f kg-reviewed HEAD                             # ユーザーが確認し終えたら、目印を今の位置に動かす
```

| 誤りの種類 | 取り消し方 |
|---|---|
| 探究そのものに誤りがあった（処理の誤りなど） | `status: invalid`（3.6）。誤りの記録として残す |
| 登録の仕方が誤っていた（ノードにすべきでないものをノードにした、リンクの張り違い） | 該当コミットを `git revert` するか、該当箇所を直す |

確認前のノードを親として使ってよい。後で親が invalid になっても、3.6 の手順で影響する子ノードを洗い出せる。

## 7. 新しいプロジェクトを作るとき

`templates/project/` の中身をプロジェクトのルートにコピーする。

```
<プロジェクト>/
├── AGENTS.md          ← プロジェクトの説明と、常に守ること。Copilot などはこれを直接読む
├── CLAUDE.md          ← 「@AGENTS.md」の1行。Claude Code はこれ経由で AGENTS.md を読む
├── .gitignore
├── decisions/
└── trials/INDEX.md
```

`AGENTS.md` の冒頭（目的、外に提供するもの）を埋める。規約の文面は `AGENTS.md` だけに書き、`CLAUDE.md` には書かない（同じ規約が2か所にあると、片方だけ更新されて食い違うため）。

## 8. 複数のプロジェクト

- プロジェクトごとに独立した Git リポジトリにする
- 全プロジェクトの一覧を、プロジェクト群の親フォルダの `PROJECTS.md` に書く（名前・1行の目的・状態・依存しているプロジェクト）。ひな形は `templates/workspace/PROJECTS.md`
- 他のプロジェクトから使われるプロジェクトは、`AGENTS.md` の「外に提供するもの」に、使い方を数行で書く。使う側のエージェントはそこだけ読めばよい
- ノードは、その探究を行ったプロジェクトの `trials/` に置く

## 9. 管理体制のサンプル（非公開）

`~/dev-management-private/samples/` に、過去のプロジェクトで採った構造と、標準のルールから変えた点・その理由がある。非公開リポジトリなので、無い環境もある。

- この管理ルール自体の改善を議論するときは、ここを読んで材料にする
- 新しいプロジェクトの構造を決めるときは、似た種類のサンプルがあれば参考として示す
- サンプルの追加・変更は、ユーザーの指示があるときだけ行う

## 10. Claude Code を使う場合

ここは Claude Code 固有の仕組みで、他の環境では使わない。

- **実装担当のサブエージェント**：プラグインの `agents/implementer.md`。ノードの `instructions.md`（ひな形 `templates/node/instructions.md`）に従って実装・実行する。設計と指示書の作成はメインの会話で行い、実装と実行をこの担当に任せる（[Claude Code: Subagents](https://code.claude.com/docs/en/subagents)）
- **実行前コミットを強制したい場合**：hooks で、実行コマンドの前に `git status --porcelain` を検査して止めることができる（[Claude Code: Hooks](https://code.claude.com/docs/en/hooks)）

## 11. してはいけないこと

- ノードのフォルダを移動・削除する
- ノード本体の md を削除する
- `outputs/` や学習済み重みを Git に入れる
- 未コミットの変更が残ったまま実験を実行する
- invalid のノードの結果・知見を根拠にする
- 実装変更と記録の更新を1つのコミットに混ぜる
- 公開リポジトリ（dev-management）に、会社や特定のプロジェクトの情報を書く
