# writing-loop

解説文書やチャットの回答を読んで止まった経験を、その場の修正と、次に書くときの書き方の両方に使うための手順と、そのデータの置き場。

```
writing-loop/
├── README.md         この手順
├── lessons.md        教訓（事例から取り出した、場面を越えて使える書き方。書く前に通して読む）
├── expressions.md    表現の辞書（分かりにくかった言い回しと、代わりの書き方の表）
└── records/          事例集（意味・意図が取れなかった事例。1件1ファイル。教訓の根拠）
```

概念を知らなくて尋ねた質問は、ここではなく `../dictionary/` で扱う。

## 0. 3つの層

| 層 | 置き場 | 中身 | いつ読むか |
|---|---|---|---|
| 原則 | 公開側の Skill（research-explainer-style） | 何を目指すか。場面を限らない | Skill が読み込まれたとき |
| 教訓 | `lessons.md` | 原則を、どの場面で外しやすいか・その場面で何を書くかまで具体にしたもの。代表例（直す前と直した後）を1組持つ | **書く前に毎回、通して読む** |
| 事例 | `records/` | 読み手が実際に止まった1件。国語の問題のように、本文・読み手の質問・欠けていたもの・直した本文を揃えて残す | 教訓を作る・見直すとき。教訓の代表例を確かめたいとき |

1件ずつの事例は、その会話に固有なので、並べて読ませても次に書くときの助けになりにくい。そこで事例から教訓を取り出し、書くときには主に教訓を読む。この形は、エージェントの失敗から教訓を取り出して短い手引きを育てる研究（ACE、Dynamic Cheatsheet、ExpeL）と、利用者が直した文から好みを言葉で推定する研究（CIPHER）を参考にした。

教訓を Skill の原則に上げるか（ルール化）は、§6 のとおりユーザーが始めたときだけ決める。それまで教訓は、近い原則から参照される形でここに溜めておく。

## 1. 止まった質問・指摘を受けたときの手順

対象は、読み手が文書や回答を読んで止まったことを示す質問と、記述への指摘。知らない概念の解説の依頼は対象外（`../dictionary/README.md`）。

1. **意図の確認**：何が分からなかったと理解したかを言い直し、読み手の返答を待つ。言い直しには、対象の記述（原文の引用）、分からなかった中身、**意味の問題か表現の問題か**を含める。解釈が一通りにしか取れないときは省いてよい（詳細は research-explainer-style の原則9 段階1）。省いてよいかは慎重に判断する。省いて答えた結果、意図とずれていたことがある
2. **回答**：合意した解釈に答える
3. **直し方の提案**：本文をどう直すかを、書き直した文そのものを示して提案する。意味の問題なら、自律レビューの診断の分類（知識／表現／正確性の軸と型）を当てて、既存のルールで直せるものはそれで直す。表現の問題なら、代わりの言い回しを示す
4. **合意したら直して、残す**：文書をその場で直す（指摘を溜めない。書き手のサブエージェントも使わない）。同時に次のとおり残す。読み手の指示を待たない

| 問題の種類 | 何が起きているか | 残す先 |
|---|---|---|
| 意味・意図 | 文の言っていることが掴めない（前提が無い、論理がつながらない、要らない文が流れに入っている） | `records/` に1件。あわせて教訓に当てはめる（§3） |
| 表現 | 言っていることは追えるが、言い回しのせいで頭に入らない（英語の直訳調など） | `expressions.md` に1行 |

両方に当たるときは、両方に残す。

`~/dev-management-private/.read-only` がある PC（会社の PC など）では、4 の「残す」を行わない（`../README.md`「読むだけの PC」）。

**残す前に、似たものが既にないか探す。** あれば読み手に示し、新しく足すか、既存のものと統合するかを確認する。事例集と辞書は、追記を続けるだけの記録ではなく、引いて使う参照データだから。

## 2. 事例集（records/）

ファイル名は `R<3桁の通し番号>.md`。通し番号は `records/` の中の最大の番号に1を足す。`records/_template.md` をコピーして使う。

- **本文**：読み手が読んだ文章を、それだけで状況が分かる範囲で載せる。表を指して止まったなら表ごと、前後の文が要るなら前後ごと載せる。1文だけを抜き出すと、後で読んだときに何の話か分からない
- **読み手の質問**：原文のまま書く。言い直さない
- **欠けていたもの**：何を書いていなかったために（または、何が余計に入っていたために）、何が理解できなかったかを書く。この会話を見なくても意味が通る文で書く。「表のほかの欄が〜に見える」のように、本文に無いものを前提にした書き方をしない
- **直した本文**：合意して書き直した本文。文を消したなら、消したことと、消した後の形を書く
- **教訓**：当てはめた教訓の番号（§3）。どれにも当たらなければ「なし」

## 3. 教訓（lessons.md）

1ファイルに、教訓を `### L<番号>` の見出しで並べる。書式は `lessons.md` の冒頭にある。

- **場面**：どんな文を書いているときに外しやすいか。教訓が原則の言い換えで終わらないための要。場面が書けないなら、それは教訓ではなく原則の繰り返しである
- **書くこと**：その場面で何を書くか
- **代表例**：その場面で実際に起きた、直す前と直した後の文の組。事例の番号で指す
- **事例**：根拠になった事例の番号。何件の事例が支えているかが見える
- **原則**：どの原則を具体にしたものか。当たる原則が無ければ「該当なし」と書く（まだ原則になっていない問題）。無理に当てはめない

事例を1件残したら、次のどちらかを、読み手の合意を取ってから行う。

- **既存の教訓に当てはまる**：その教訓の「事例」に番号を足す。代表例がもっと良ければ差し替える。場面や書くことの範囲が広がるなら書き直す
- **どれにも当てはまらない**：新しい教訓の案を示す

教訓は仮の切り方である。事例が増えると、1つの教訓が2つに分かれたり、2つが1つにまとまったりする。切り直したときは、事例の「教訓」の欄も直す。

## 4. 表現の辞書（expressions.md）

1ファイルの表。書くときに通して引く参照表として使う。列は「分かりにくかった表現・型・代わりの書き方」の3つで、出典は書かない。「型」は直訳調・硬い漢語・指示語の多用などの分類で、ルール化のときに共通点を探す手がかりにする。

## 5. 使う人

| 使う人 | 教訓 | 事例集 | 表現の辞書 |
|---|---|---|---|
| 文書を書く・回答するエージェント | 書く前に通して読み、当てはまる場面ではそれに従う | 教訓の代表例を確かめたいときに読む | 書く前に引き、載った表現を使わない |
| 自律レビューの読み手（読み手の写し鏡のモデル） | 渡さない（「書くこと」は直し方なので、読み手を検査役にしてしまう） | 本文・読み手の質問・欠けていたものだけを渡す。同じところで止まる感覚を持たせるため | 表現と型だけを渡す。載った表現が出てきたら止まる |
| 自律レビューの書き手 | 書く前に読む | 教訓から辿って読む | 書く前に引く |

## 6. ルール化

ユーザーが任意のタイミングで始める。記録の件数などの決まった目安は置かず、エージェントから始めたり提案したりしない。

始まったら、エージェントは教訓と、その根拠の事例を並べた表を用意する。教訓ごとに、既存の原則との関係（原則の具体化として上げる／新しい原則にする／教訓のまま残す）の選択肢と書き直し例を示し、ユーザーと一緒に決める。決まったルールを公開側の Skill に書き、版を上げる。ルールには根拠になった教訓と事例の番号を書く。

事例そのものは Skill に書き写さない。Skill には原則を書き、具体は教訓と事例から参照させる。

## 7. エージェントがこの手順を知る経路

このリポジトリは非公開なので、中身を公開側に書かずに、場所と入口だけを公開側の Skill に置いている。

| 置き場所 | 書いてあること | 読み込まれるとき |
|---|---|---|
| `../device-instructions.md`（個人設定から読み込む） | 止まった質問を受けたらこの README に従う、書く前に辞書と教訓を引く | 毎回（どのプロジェクトの会話でも） |
| research-explainer-style の原則3・原則9 | 辞書と事例集の場所、この手順への入口 | 説明を書くとき、指摘を受けたとき |
| project-rules の9節 | このリポジトリに `writing-loop/` と `dictionary/` があること | プロジェクトの作業で project-rules が読み込まれたとき |

research-explainer-style の各原則には「`records/` のうち『原則：N』の記録を読む」と書いてあるが、事例には「原則」の欄が無くなり、原則は教訓の側に書くようにした。Skill を改訂するまでは、この1行を「`lessons.md` のうち原則 N の教訓を読み、必要ならそこから事例へ辿る」と読み替える（`../device-instructions.md` にも書いてある）。

## 8. 置き場とコミット

どのプロジェクトの会話で生まれたものでも、このリポジトリに置いてコミットする。作業中のプロジェクトのリポジトリには入れない。push はユーザーが指示したときだけ行う（`../README.md`）。
