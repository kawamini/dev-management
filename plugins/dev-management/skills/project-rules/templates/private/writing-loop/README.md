# writing-loop

解説文書やチャットの回答を読んで止まった経験を、その場の修正と、書き方の Skill（公開側の research 系・explainer 系）の改訂の両方に使うための手順と、そのデータの置き場。

```
writing-loop/
├── README.md         この手順
├── expressions.md    表現の辞書（分かりにくかった言い回しと、代わりの書き方の表）
└── records/          事例集（意味・意図が取れなかった事例。1件1ファイル）
```

概念を知らなくて尋ねた質問は、ここではなく `../dictionary/` で扱う。

## 1. 止まった質問・指摘を受けたときの手順

対象は、読み手が文書や回答を読んで止まったことを示す質問と、記述への指摘。知らない概念の解説の依頼は対象外（`../dictionary/README.md`）。

1. **意図の確認**：何が分からなかったと理解したかを言い直し、読み手の返答を待つ。言い直しには、対象の記述（原文の引用）、分からなかった中身、**意味の問題か表現の問題か**を含める。解釈が一通りにしか取れないときは省いてよい（詳細は research-explainer-style の原則9 段階1）
2. **回答**：合意した解釈に答える
3. **直し方の提案**：本文をどう直すかを、書き直した文そのものを示して提案する。意味の問題なら、自律レビューの診断の分類（知識／表現／正確性の軸と型）を当てて、既存のルールで直せるものはそれで直す。表現の問題なら、代わりの言い回しを示す
4. **合意したら直して、残す**：文書をその場で直す（指摘を溜めない。書き手のサブエージェントも使わない）。同時に次のとおり残す。読み手の指示を待たない

| 問題の種類 | 何が起きているか | 残す先 |
|---|---|---|
| 意味・意図 | 文の言っていることが掴めない（前提が無い、論理がつながらない） | `records/` に1件 |
| 表現 | 言っていることは追えるが、言い回しのせいで頭に入らない（英語の直訳調など） | `expressions.md` に1行 |

両方に当たるときは、両方に残す。

`~/dev-management-private/.read-only` がある PC（会社の PC など）では、4 の「残す」を行わない（`../README.md`「読むだけの PC」）。

**残す前に、似たものが既にないか探す。** あれば読み手に示し、新しく足すか、既存のものと統合するかを確認する。事例集と辞書は、追記を続けるだけの記録ではなく、引いて使う参照データだから。

## 2. 事例集（records/）

ファイル名は `R<3桁の通し番号>.md`。通し番号は `records/` の中の最大の番号に1を足す。`records/_template.md` をコピーして使う。

- 「原則」の欄に、research-explainer-style のどの原則の事例かを番号で書く（複数可）。Skill の各原則は作った例を持たず、「`records/` のうち『原則：N』の記録を読む」とだけ書いてある。エージェントは原則 N に関わる文を書くとき、その原則の記録だけを読む
- 「対象」には、プロジェクト名と文書のパスと節を書く
- 統合した記録は、統合した元の番号を「似た記録」に残す

## 3. 表現の辞書（expressions.md）

1ファイルの表。書くときに通して引く参照表として使う。列は「分かりにくかった表現・型・代わりの書き方」の3つで、出典は書かない。「型」は直訳調・硬い漢語・指示語の多用などの分類で、ルール化のときに共通点を探す手がかりにする。

## 4. 使う人

| 使う人 | 事例集 | 表現の辞書 |
|---|---|---|
| 文書を書く・回答するエージェント | Skill の原則から参照して読む | 書く前に引き、載った表現を使わない |
| 自律レビューの読み手（読み手の写し鏡のモデル） | 渡す。同じところで止まる感覚を持たせるため | 渡す。載った表現が出てきたら止まる |

## 5. ルール化

ユーザーが任意のタイミングで始める。記録の件数などの決まった目安は置かず、エージェントから始めたり提案したりしない。

始まったら、エージェントは記録を並べた表、止まった箇所に説明があったか、既存ルールとの関係（統合／補足／新規）の選択肢と書き直し例を用意し、ユーザーと一緒に言語化して決める。決まったルールを公開側の Skill に書き、版を上げる。ルールには根拠になった記録の番号を書く。

事例そのものは Skill に書き写さない。Skill には原則を書き、事例は `records/` から参照させる。

## 6. エージェントがこの手順を知る経路

このリポジトリは非公開なので、中身を公開側に書かずに、場所と入口だけを公開側の Skill に置いている。

| 置き場所 | 書いてあること | 読み込まれるとき |
|---|---|---|
| `../device-instructions.md`（個人設定から読み込む） | 止まった質問を受けたらこの README に従う、書く前に辞書を引く | 毎回（どのプロジェクトの会話でも） |
| research-explainer-style の原則3・原則9 | 辞書と事例集の場所、この手順への入口 | 説明を書くとき、指摘を受けたとき |
| project-rules の9節 | このリポジトリに `writing-loop/` と `dictionary/` があること | プロジェクトの作業で project-rules が読み込まれたとき |

## 7. 置き場とコミット

どのプロジェクトの会話で生まれたものでも、このリポジトリに置いてコミットする。作業中のプロジェクトのリポジトリには入れない。push はユーザーが指示したときだけ行う（`../README.md`）。
