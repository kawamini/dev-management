# writing-loop

解説文書やチャットの回答を読んで止まった経験を材料に、書き方の Skill（公開側の explainer 系・research 系）を改訂していくための記録。

## 流れ（合意済みの骨格）

1. **意図の確認**：質問を受けたら、エージェントは何が分からなかったと理解したかを、対象の記述（原文）と分からなかった中身を特定して言い直す。合意してから答える
2. **記録**：ユーザーが「これを記録して」と指示したときだけ、エージェントが下書きを作り、ユーザーが直して `records/` に保存する。エージェントから記録を提案しない
3. **ルール化**：ユーザーが任意のタイミングで始める。記録の件数などの決まった目安は置かず、エージェントから始めたり提案したりしない。始まったら、エージェントは記録を並べた表、止まった箇所に説明があったか、既存ルールとの関係（統合／補足／few-shot／新規）の選択肢と書き直し例を用意し、ユーザーと一緒に言語化して決める
4. **反映**：決まったルールを公開側の Skill に書き、版を上げる。ルールには根拠になった記録の番号を書く

### 1 の対象（方向性。最初のルール化で原則9に反映する）

意図の確認が要るのは、読み手が「分からない」「意味が理解できない」「意図が理解できない」と止まった質問である。これがループの改善の対象になる。

一方、読み手が知らないものの解説を求める依頼（例：「`git rebase` とは何か」）は、何を説明すればよいかが依頼の文面で決まっているので、確認のやり取りをせずに答える。

1 は、今の explainer-style・research-explainer-style の原則9（既定では止まらずに答える）と食い違っている。原則9 の段階1 は、最初のルール化で上の対象に合わせて見直す。それまでは、エージェントは今の原則9 に従う。

## エージェントがこのループを知る経路

このリポジトリは非公開なので、中身を公開側に書かずに、場所と入口だけを公開側の Skill に置いている。

いちばん確実なのは、デバイスごとの個人設定から読み込む `../device-instructions.md` である。毎回読まれるので、ユーザーが Skill の名前を言わなくても、記録の指示がここにつながる。公開側の Skill は、それを補う入口である。

| 置き場所 | 書いてあること | 読み込まれるとき |
|---|---|---|
| `../device-instructions.md`（個人設定から読み込む） | 記録を指示されたら、この README の手順に従うこと | 毎回（どのプロジェクトの会話でも） |
| explainer-style・research-explainer-style の `description` | 「記録して」と指示されたときに発動すること | 常に（Skill の説明は毎回エージェントの視野にある） |
| 同じ Skill の原則9「記録と、この Skill の改訂」 | このリポジトリの場所、記録とルール化を始める条件、記録の置き場 | 上の説明に合う依頼が来て、Skill の本文が読み込まれたとき |
| project-rules の9節 | このリポジトリに `writing-loop/` があること | プロジェクトの作業で project-rules が読み込まれたとき |

## 記録の置き場とコミット

- どのプロジェクトの会話で「記録して」と指示されても、記録はこのリポジトリの `records/` に置き、このリポジトリにコミットする。作業中のプロジェクトのリポジトリには入れない
- 「対象」には、プロジェクト名と文書のパス（例：`<プロジェクト名>/trials/T001-<内容>/report.md` の「全体像」）を書く
- 通し番号は、`records/` の中の最大の番号に1を足す

## 記録の書式（暫定）

ファイル名は `R<3桁の通し番号>.md`。`records/_template.md` をコピーして使う。書式は最初のルール化のときに見直す。
