# Research Citation

研究解説における **「出典・一次情報・リンク」** の規範を定義する Skill。
文章スタイルは `research-explainer-style`、構造設計は `research-structure` に分離されている。

## なぜこのSkillが必要か

研究者は **公式ドキュメント・論文・一次情報と本解説を行き来できる状態** を必要とする。
解説が「だいたい正しい」だけでは、研究者は不安になって自分で公式を辿り直すことになり、解説の意味が薄れる。

**読者が解説と一次情報を1クリックで行き来できる状態を最優先する**。これは親切ではなく、研究解説の必須要件。

## コア原則

### 原則1：一次情報の事前確認（最重要）

研究解説の対象が公式ドキュメント・論文・コードベースを持つ場合、その構造を **書き始める前に直接確認する**。

#### 必須ルール

1. **公式構造の事前 fetch**：公式ドキュメントの章構造（サイドバー、目次、TOC）を直接 fetch して確認してから解説を書く。本文中で見かけたリンク名を上位章と勘違いしない。

2. **動的サイドバー対策**：公式ドキュメントのサイドバーが JavaScript 動的生成で web_fetch では取れない場合、次のいずれかで補う：
   - PDF版の目次を取得（大きすぎる時は最初の数ページのみ）
   - 「次へ」リンクを連鎖的に辿って章順序を確認
   - **取れない場合はユーザーに直接尋ねる（推定禁止）**

3. **「確認できない」の明示**：確認していない章名・分類・対応関係は **必ず** 以下のいずれかにする：
   - `⚠️ 要検証` マークと共に出す
   - ユーザーにその旨を伝えて教えてもらう
   - 一旦保留にして他の確実な部分だけ進める

   **推定で進めて間違いを重ねるのが最悪のパターン**。

### 原則2：リンク密度の規範

解説中に登場する公式の概念・機能・APIには、**公式ページに該当箇所がある限り必ず**インラインリンクを付ける。判定基準は「該当ページが存在するか」であって、手間ではない。

#### 何にリンクを付けるか

- 公式ドキュメントの章名・節名
- API名・関数名
- 製品名・機能名
- 重要な技術用語（公式の解説ページがあるもの）
- 数値・仕様（出典が公式ページにあるもの）

#### リンクのつけ方

```markdown
[公式: Model training](https://docs.aws.amazon.com/sagemaker/latest/dg/train-model.html) では、
学習を3段階（Before / During / After）に分けて整理している。
```

「ここに書いてあるはず」ではなく **「該当ページの該当セクション」までリンク** を狙う。

#### 一次情報が URL を持たない場合（論文 PDF など）

論文には公式ドキュメントのような URL 付きの章構造がないことが多い。その場合はリンクの代わりに、参照箇所を番号で特定する。番号による特定は、リンクの代替として同等に扱う。

**本文には参照の番号 `(ref. n)` だけを置き、場所と原文は参照箇所のまとめに書く。** Section・Table の番号や原文の引用を本文の括弧に入れると、括弧が長くなって文の流れが切れるからである（2026-11-08、閲読ガイドへの指摘による）。

本文：

> 著者らは学習率を 1e-4 に固定している (ref. 4)。

参照箇所のまとめ（多ファイル解説なら `98_sources.md`、1ファイルの解説ならファイル末尾の「参照箇所」節）：

```markdown
### ref. 4
- 場所：Section 4.1 第2段落（p.6）、Table 3
- 原文：We fix the learning rate to 1e-4 ...
- 使った箇所：03 §2
```

- 本文の `(ref. n)` から、まとめの該当箇所へリンクで飛べるようにする（`[(ref. 4)](./98_sources.md#ref-4)` の形。見出しの書き方とリンク先は、読み手の環境で飛べることを確かめて決める）
- 番号は解説全体で通し番号にする。同じ箇所を2度参照するなら、同じ番号を使う
- 1つの段落が論文の1つの段落をまとめたものなら、段落の終わりに1つ置けばよい。主張ごとに置かなくてよい
- 論文の参考文献の番号（「RT-2 [1]」の [1]）は、形が違うので本文に残してよい
- 本文で「Figure 2」「Table 3」と番号を出すのは、その図や表を載せて説明するときだけにする（`research-structure` 原則6）

arXiv の HTML 版など、節単位の URL が実在する場合は、まとめの「場所」にリンクを付ける。

### 原則3：用語の正確性（目的依存の判断）

**用語の正確性は目的依存**。一律ルールではなく、以下の場合分けで判断する。

#### 場合分け

| 解説の目的 | 用語の使い方 |
|---|---|
| **公式ドキュメントを解説する場面**（読者を公式に辿らせるのが目的） | 正確な章名・API名・公式表記を **必須** とする。書き下した表現を公式名のように使うのは厳禁 |
| **概念整理として参照する場面**（理解を助けるのが目的） | 書き下した表現でよい。ただし「公式の正式名は〇〇」と並記する |

#### 書き下し表現の活用パターン

並記すれば、読みやすさと正確性を両立できる：

```markdown
Training Job（学習ジョブ。公式ガイドの章タイトルは [Model training](URL)）

エンドポイント（公式: [Real-time endpoints](URL)）

trainer.train() の1行（裏では CreateTrainingJob API を呼んでいる）
```

#### 避けるべき混同

- **公式の章タイトル と API名 の混同**：「CreateTrainingJob」は API 名、「Model training」は章タイトル。前者を後者の代わりに使わない
- **本文中のリンク名 と 上位章名 の混同**：あるページの本文中に `[Label Data](URL)` というリンクがあっても、それが公式ガイドのトップレベル章とは限らない。サイドバーを確認すること
- **書き下し表現を公式名のように使う**：「3つのモード」のような独自整理は、公式分類のように使ってはならない。独自整理だと明示する

### 原則4：推測の排除と「⚠️ 要検証」マーク

一次資料で確認できなかった事実は、推測で埋めず **「⚠️ 要検証」** と明示する：

> ⚠️ 要検証：この学習データセットの規模は本文中に明示されておらず、推定値です

#### マーク基準

- 公式に明記されていないが推測した数値 → ⚠️ 要検証
- 確認していないが概ねこうだろうと思った仕様 → ⚠️ 要検証
- 出典のURLが手元になく、記憶ベースで書いた内容 → ⚠️ 要検証

「書いた内容について、どうしてそう判断したか」が読み手に追跡可能な状態を最優先する。

#### 一次資料から**導いた**ことは、⚠️ ではなく身分を明示して書く

一次資料に書かれていないことには2種類ある。混同すると、どちらも読み手に正しく届かない。

| | 書き方 |
|---|---|
| **一次資料から決まらない**（情報がない） | `⚠️ 要検証` を付ける。推測の中身を書くなら、推測であることと何が確認できなかったかを書く |
| **一次資料には無いが、一次資料の記述から導ける** | `⚠️` を付けない。**誰の推論かを明示**し、根拠にした記述を示す。例：「この解釈は、Appendix D.1 のコード比較から導いたもので、論文にこの記述はない」 |

後者に `⚠️ 要検証` を付けると、読み手は「確認されていない話」として割り引く。無印で書くと一次資料の主張に見える。**どちらでもない身分があることを、本文で示す。**

**`⚠️` は確認を怠ったことの免罪符ではない。** 一次資料を開けば確認できることに `⚠️` を付けてはならない。判断に迷ったら、まず一次資料の該当箇所を開く。

### 原則5：出典の透明性

**「どんなページを調べたか」が読み手に分かる状態** を作る。

#### 必須要素

1. **解説の冒頭で「主な出典」を明示**：
   ```markdown
   **主な出典**: [Amazon SageMaker AI Developer Guide](https://docs.aws.amazon.com/sagemaker/latest/dg/whatis.html)
   ```

2. **論文解説の場合は claim ごとに出典を示す**（形は原則2 の `(ref. n)`）：
   > 著者らは ... と結論している (ref. 7)。

3. **本文中の引用は「公式のこの箇所」と特定する**：
   - 「[Model training](URL) によれば」のように引用元を明示
   - 「公式ドキュメントには」のような曖昧な引用は避ける

4. **複数のソースを使った場合は併記**：
   ```markdown
   **主な出典**:
   - [SageMaker AI Developer Guide](URL1)
   - [SageMaker Python SDK Documentation](URL2)
   - [AWS Deep Learning Containers Release Notes](URL3)
   ```

## 公式ドキュメントを解説するときの実装手順

研究者が公式ドキュメントを読解するための補助として解説する場合、以下の順で進める：

1. **公式トップページを fetch して構造を確認**
2. **サイドバー/目次の取得を試みる**：
   - 直接取得できれば確実
   - 取得できなければ PDF版の目次
   - それも無理ならユーザーに尋ねる
3. **上位2階層程度をマップとして書き出す**
4. **解説対象の章を特定し、その URL を明示**
5. **解説本文中で、参照する箇所ごとにリンクを付ける**
6. **書き下し表現を使う場合は「公式: 〇〇」と並記**

## 出力前セルフチェック（必須手続き）

本文を出力する前に、次の6項目を順に検査する。1つでも不合格があれば修正してから出す。

1. **冒頭出典**：「主な出典」が冒頭にあるか。複数ソースなら併記されているか
2. **claim 単位の出典**：論文解説なら、各 claim に `(ref. n)` があり、参照箇所のまとめに場所と原文があるか。本文の括弧に Section の番号や原文の引用が残っていないか
3. **リンク漏れ**：公式に該当ページがある用語・章名・API名に、リンクなしの言及が残っていないか
4. **⚠️ の付け漏れ**：記憶ベース・推測ベースで書いた箇所を上から順に探し、すべてに「⚠️ 要検証」が付いているか
5. **⚠️ の付けすぎ**：⚠️ を付けた箇所を上から順に見て、(1) 一次資料を開けば確認できるものに付けていないか、(2) 一次資料から**導いた**推論に付けていないか（後者は ⚠️ ではなく身分の明示。原則4）
6. **公式名と書き下しの区別**：独自整理・書き下し表現が公式名のように読める箇所が残っていないか

## 禁止事項

- **推定で章名を書く**：公式の章構造を確認せず「だいたいこういう章があるはず」と書く
- **本文中のリンク名を上位章と混同**：あるページの本文に出てくるリンクが、公式の上位章とは限らない
- **公式名と書き下し表現の混在**：書き下し表現を公式名であるかのように扱う
- **リンクなしの公式名言及**：公式ドキュメントに該当ページがある用語を、リンクなしで出す
- **記憶ベースの記述**：「確か○○だったはず」で済ませる。確認するか「⚠️ 要検証」を付ける
- **セルフチェックを飛ばさない**：出力前セルフチェックは必須手続き

## このSkillの改訂方針

このSkillは運用の中で改訂される前提で書かれている。改訂の兆候：

- 読者が「公式ページを辿れない」「どこを参照しているか分からない」と指摘した
- 「⚠️ 要検証」を付けるべき箇所に付けていなかった
- 解説の章構造と公式の章構造がずれていた

これらが見えたら、対応する原則を具体化する。
