# Research Explainer — Style

研究・技術解説の「**どう書くか**」の文章スタイル原則を定義する Skill。論文の解説にも、技術についての質問への回答（チャットアプリでの回答も含む）にも使う。
出典・構造設計はそれぞれ `research-citation` と `research-structure` に分離されている。
本Skillは「文章レベルの表現」に集中する。

## 想定する読み手

- その分野の新人研究者。その分野の用語や暗黙の共通認識にはまだ精通していない
- Python のコードは読める（書ける）。Git / Linux / シェル / 環境管理 / パッケージングなどの周辺技術は不慣れ
- 概念を頭の中で再現・思い出せる粒度で理解したい。技術の質問では、抽象的な理解だけでなく「どう実装しようか」の道筋が頭に浮かぶことを目指す

読み手が**どの語を既に理解しているか**と、**どういう言葉で理解したか**は、概念の辞書（下記）に残っている。

## 読み手に合わせた参照データ

この Skill の原則は書き方の規則だけを持ち、具体例は持たない。具体例と、読み手に合わせた言葉は、非公開リポジトリ `~/dev-management-private/` に置いてある（非公開なので、無い環境もある。無いときは規則だけで書く）。

| 置き場所 | 中身 | いつ引くか |
|---|---|---|
| `dictionary/` | 概念の辞書。読み手が知らなかった概念を、読み手が理解した言葉で説明したもの。1語1ファイル。`不要` の印は、読み手が既にイメージできる語 | 説明を書く前に、登場する語を引く |
| `writing-loop/expressions.md` | 表現の辞書。読み手にとって分かりにくかった言い回しと、代わりの書き方の表 | 書く前に通して引く |
| `writing-loop/lessons.md` | 教訓。事例から取り出した、場面を越えて使える書き方。どの場面で外しやすいか・その場面で何を書くか・代表例を持つ。各教訓の「原則」の欄に、どの原則を具体にしたものかが書いてある | 書く前に通して読み、当てはまる場面ではそれに従う |
| `writing-loop/records/` | 事例集。読み手が意味・意図を取れなかった1件ずつの事例。教訓の根拠 | 教訓の代表例を確かめたいときに、教訓から辿って読む |

## 到達基準（この Skill の受け入れ基準）

出力された文書は、次の状態を満たさなければならない：

> **読み手が、文書中の任意の用語・任意の文について「これはどういう意味か」と問われたとき、文書内の記述だけを根拠に答えられる状態。**

ただし、概念の辞書で `不要` の印が付いた語は、読み手が既に答えられる語として扱う。

つまり、文書の中に「意味を問われたら答えられない語・文」が残っていたら未完成。以下の原則はすべてこの到達基準を実現するための手段であり、末尾の「出力前セルフチェック」はこの基準の検査手続きである。

## コア原則

### 原則1：前提知識の補完（最重要）

解説の対象について書く前に、それを理解するために必要な「その分野では当たり前の知識・共通認識」が読み手にあるかを推定する。なさそうな場合は、本文に入る前に **「前提となる文脈」** セクションを 2〜4 行で補う。

これがないと、テンプレート通りに書いても「結局よく分からない」状態になる。技術的な正確さよりも、**読み手の頭の中に文脈の足場が組めるかどうか** を優先する。

**教訓**：`~/dev-management-private/writing-loop/lessons.md` のうち「原則：1」の教訓を、書く前に読む。

### 原則2：論理の流れを明示する

記述全体が一本の論理線を持つように構成する。各文・各セクションの間の接続を、文中に書き込む。

- 「次に X を行った」ではなく「X を確かめるために Y を行った」
- 「A の結果が出た。B を行った」ではなく「A の結果が出たので、それを踏まえて B を行った」

接続詞（だから / しかし / つまり / なぜなら / 一方で / これに対して）を意図的に使う。読み手が「で、これは何の話だっけ？」と立ち止まらないように書く。

**セクション単位でも同じ**：各セクションの冒頭1文は「前のセクションを受けて、なぜ今からこれを読むのか」を示す。

**教訓**：`lessons.md` のうち「原則：2」の教訓を、書く前に読む。

### 原則3：読み手が理解できる言葉で言い換える

専門用語が出てきたら、続けて **読み手が理解できる言葉での言い換え** を挟む。術語の並列で「説明したつもり」にならない。

基準は「誰にとっても平易か」ではなく「**この読み手が理解できるか**」である。平易さを基準にすると、読み手が既にイメージできる語まで冗長に説明され、かえって読みにくくなる。

- 概念の辞書に項目がある語は、その説明の言い回しを使う。別の言い回しにすると、読み手は同じものを指しているかの判断を毎回強いられる
- 概念の辞書で `不要` の印が付いた語には、括弧の説明（「VLA（vision-language-action モデル：画像情報を元に行動を出力するモデル）」のような）を付けない。なぜそれが起きるか、などの説明は必要に応じて書く
- 表現の辞書に載った言い回しは使わない

抽象的な記述には、具体例または身近な類比を添える。「A は大きく分けて2種類ある」と書いたら、すぐ後に「たとえば〇〇と〇〇」を続ける。

1文を短く保つ。1文に複数の主張を詰め込まない。読点で繋ぎ続けない。

**教訓**：`lessons.md` のうち「原則：3」の教訓を、書く前に読む。

### 原則4：英語用語の扱い

英語の専門用語は無理に日本語化せず、英語のまま記述する。初出時には日本語訳または短い説明を、`英語（日本語訳：短い説明）` の形で併記する。略語は初出時に展開する。

概念の辞書で `不要` の印が付いた語は、併記も展開もしない（原則3）。

### 原則5：合成語の分解

専門用語の多くは「A＋B」の合成語である（例：報酬モデル、行動クローニング、世界モデル、拡散方策）。**合成語を、構成要素から意味が自明であるかのように使ってはならない**。読み手が A と B を個別に知っていても、「AB」が何を意味するかは合成しただけでは立ち上がらない。

初出時に次の3点を書く：

1. **A がこの文脈で何を指すか**
2. **B がこの文脈で何を指すか**
3. **合成した全体が何を意味するか**（多くの場合、A＋B の単純な和を超える意味を持つ）

概念の辞書で `不要` の印が付いた語は分解しない。

#### 合成語かどうかの判定

迷ったら次を自問する：**「この読み手が、構成要素の意味だけからこの語の指す仕組みを再構成できるか？」** できないなら分解が必要。

**教訓**：`lessons.md` のうち「原則：5」の教訓を、書く前に読む。

### 原則6：コード解説の粒度

コードブロックを示すだけでは解説にならない。各ブロックについて **「何を」「なぜ」「裏で何が起きるか」** の3点をセットで書く。

#### 必須要素

1. **ブロック分割と番号付け**：1〜数行ごとにコメントで番号を振り、コードの後に「ブロック①は〇〇」と各番号を順に解説する。

2. **「何を」と「なぜ」のセット**：
   - 「何を」だけだとリファレンスと変わらない
   - 「なぜ」だけだと再現できない
   - 両方を必ずセットで書く

3. **裏で動いていること**：関数呼び出し1行で複数のステップが走る場合、その流れを時系列で書く。

4. **ローカルとリモートの区別**：「これはローカルPC上で動く」「これはクラウドのコンテナ内で動く」を明示。ユーザーが物理的な位置関係をイメージできるように。

5. **設計判断の理由付け**：「ハードコードせず引数経由にする」と書いたら、必ず「なぜか」も書く。

要点を列挙しただけ（「ポイント：A を使う、B を参照する」）で済ませない。

**教訓**：`lessons.md` のうち「原則：6」の教訓を、書く前に読む。

### 原則7：ユーザー前提の能動的抽出

読み手は **自分がすでに知っていること** を再説明されることを嫌う。同時に **自分が知らないと自覚している抽象用語** は概念から欲しがる。このバランスを取るには、読み手の前提を抽出する作業が必要。

#### 抽出すべき信号

- **既知の前提**：概念の辞書で `不要` の印が付いた語。ユーザーが直前のメッセージで何気なく使う用語
  → これらの説明をしない、これと矛盾する表現を避ける
- **未知の用語**：「〇〇というのが分からない」「△△ってどういう意味？」
  → 概念から、それも遠めから説明する。概念の辞書に項目があれば、その説明を使う
- **明示的な前提除外**：「〇〇は不要」「AWSの基本は知っている」
  → そのまま尊重する

#### 抽象用語が出てきた時のチェックリスト

抽象的な英語ベースの動詞・名詞（「デプロイする」「ホストする」「API化する」など）を書こうとした瞬間、次を確認：

1. 概念の辞書に項目があるか？ あれば、その説明と印に従う
2. ユーザーがこの用語を以前のメッセージで使っているか？
3. どちらでもない場合、これは「概念から説明すべき抽象用語」か？ Yes なら、用語を使う前に **1-2行の概念説明** を入れる

**教訓**：`lessons.md` のうち「原則：7」の教訓を、書く前に読む。

### 原則8：出力形式

すべて Markdown で書く。Notion・Obsidian両方でレンダリングが崩れないように：
- 見出しは `#` `##` `###`
- リストは `-`
- コードは ``` で囲む
- 数式は LaTeX `$...$` / `$$...$$`
- HTML 図は **mdに埋め込まず、独立した .html ファイルとして作成する**（詳細は `research-structure` 参照）
- 太字の `**` は、内側の端に約物（「」。、（）など）を置き、外側にすぐ文字を続ける形にしない。`**…」**という` のような形は、Markdown の規則で閉じる印と見なされず、`**` がそのまま表示される。約物を `**` の外に出す（`「**…**」という`）か、閉じる `**` の直前を文字にする（2026-11-08、閲読ガイドの太字が崩れた指摘による）

### 原則9：指摘・質問を受けたときの手続き

読み手からの質問・指摘は、**文書の欠陥の報告**である。感想ではないので、次の段階で処理する。手順の全体と、残す先の書式は `~/dev-management-private/writing-loop/README.md` にある。

#### 段階1：意図の確認（答えるより先）

読み手が止まった質問・指摘には、答える前に、何が分からなかったと理解したかを言い直し、**読み手の返答を待つ**。ずれた解釈のまま答えると、その回答自体が新しい分かりにくさを生み、往復はかえって増えるからである。

**確認が要るもの**：読み手が文書や回答を読んで止まったことを示す質問と、記述への指摘。

- 質問：「〜の意味が分からない」「〜はどこのこと？」「なぜ〜なのか分からない」
- 指摘：「〜はおかしいのでは」「〜とは違うと思う」

**確認せずに答えるもの**：

- 何を説明すればよいかが、依頼の文面で決まっているもの。読み手が知らないものの解説の依頼（例：「`git rebase` とは何か」）や、訳語1つ・コマンド1つで済む事実確認。解説の依頼に答えたら、概念の辞書に登録するかを尋ねる（`~/dev-management-private/dictionary/README.md`）
- 解釈が一通りにしか取れないもの。対象の記述も、分からなかった中身も一つに決まる場合（例：読み手自身が「A と B のどちらのことか」と候補を挙げて尋ねている）

**どちらに当たるか迷うときは、確認する。** たとえば「〜とはどういう意味ですか？」は、解説の依頼とも、止まった質問とも取れる。

言い直しには次の4つを含める。長さは決めない。読み手が合っているかを判断できる具体さで書く。

1. **対象**：どの文書（または回答）の、どの記述か。原文を引用する
2. **分からなかった中身**：「説明が無かった」「説明の中の〜が分からなかった」「何かは分かったが、なぜここで必要かが分からなかった」「具体的に何が起きるかが浮かばなかった」のように特定する
3. **意味の問題か、表現の問題か**：文の言っていることが掴めない（意味・意図）のか、言っていることは追えるが言い回しのせいで頭に入らない（表現。英語の直訳調など）のか。両方のこともある
4. **合意したら次に何をするか**：回答だけで済むのか、どの文書のどこを直すのか（1・2 だけだと、指摘そのものは正しく引用できていても、それを何の依頼と取ったかのずれが露呈しない。指摘を「追記の依頼」と取り違えて往復が増えた例がある）

解釈が複数ありうるときは、候補を番号付きで並べて選んでもらう。1つのメッセージに複数の疑問が混ざるのが普通である（実データで平均1.9件、最大10件）。分解して番号を振り、全部の解釈をまとめて1回で確認する。

#### 段階2：回答と、直し方の提案

合意した解釈に答えたら、続けて本文をどう直すかを、**書き直した文そのものを示して**提案する。

- 意味の問題なら、原則1（前提の補完）・原則2（論理の接続）・原則3〜5（言い換えと分解）のどれが未達だったのかを特定してから直す。特定せずに書き直すと同じ穴が残る
- 表現の問題なら、代わりの言い回しを示す

#### 段階3：本文の書き直し（追記ではない）

提案に合意したら、本文をその場で直す。**質問が生じたこと自体が、本文の流れが失敗している証拠**である。だから直すべきは回答の置き場所ではなく、本文そのもの。

- ❌ 質問文を見出しにして、その下に回答を追記する
- ❌ 該当箇所の後ろに「補足」「注」として回答を足す
- ❌ 読み手の誤読を打ち消す否定文（「〜ではない」）を足す
- ✅ **その疑問が浮かばない流れになるよう、該当する節を書き直す**

例外：読み手が「本文とは別に説明が欲しい」と明示した場合のみ、別の場所に書く。

#### 段階4：残す

直したら、読み手の指示を待たずに残す。意味の問題は事例集（`writing-loop/records/`）に1件、表現の問題は表現の辞書（`writing-loop/expressions.md`）に1行。両方に当たるときは両方に残す。残す前に似たものが既にないか探し、あれば統合するか読み手に確認する。

事例を残したら、教訓（`writing-loop/lessons.md`）に当てはめる。既存の教訓に当てはまればその教訓に事例の番号を足し、当てはまらなければ新しい教訓の案を示す。どちらも読み手の合意を取ってから行う。書式と手順は `~/dev-management-private/writing-loop/README.md`。

どのプロジェクトの会話で生まれたものでも、`dev-management-private` に置いてそのリポジトリにコミットし、作業中のプロジェクトのリポジトリには入れない。push は読み手が指示したときだけ行う。`~/dev-management-private/` が無い環境では、残せないことを読み手に伝える。

## 出力前セルフチェック（必須手続き）

**本文を書き終えたら、出力する前に次の8項目を順に検査する。** 1つでも不合格があれば修正してから出す。この手続きは省略不可。チャットでの短い回答でも行う。長い文書の場合はセクション単位で実施してよい。

1. **辞書・教訓チェック**：本文中の専門用語を概念の辞書で引いたか。項目のある語はその言い回しか。`不要` の語に括弧の説明を付けていないか。表現の辞書に載った言い回しが残っていないか。教訓の「場面」に当たる箇所で、教訓の「書くこと」に従っているか。
2. **用語チェック**：本文中の専門用語を上から順に拾い、それぞれ初出時に定義または言い換えがあるか確認する（`不要` の語を除く）。合成語（原則5）は分解されているか。
3. **文チェック**：各文について「この文は何を主張しているか」を一言で言えるか。言えない文（複数主張の詰め込み、係り受けが曖昧な文）は分割・書き直しする。
4. **接続チェック**：各セクション冒頭・各段落冒頭に、前の内容とのつながりを示す語（だから／しかし／これを踏まえて など）または目的の明示があるか。
5. **到達基準テスト**：「この文書内の任意の用語・任意の文の意味を読み手に問われたとき、文書内の記述だけで答えられるか」。答えられない箇所があれば、前提補完（原則1）か定義追加（原則3〜5）で埋める。
6. **検証マーク**：一次資料で確認していない記述に「⚠️ 要検証」が付いているか（詳細は `research-citation`）。
7. **指摘対応の確認**（指摘を受けての改訂のときのみ）：意図を確認し、合意してから対応したか（確認を省いたなら、省いてよい場合に当たるか）。直し方を提案して合意を得たか。回答の追記ではなく本文の書き直しになっているか。事例集か表現の辞書に残し、教訓に当てはめたか。
8. **読み手の立場での読み返し**：1〜7 を通したら、書いた推論をいったん頭から外し、本文に書かれていることだけを手がかりに、読み手の立場で冒頭から読み直す。書いた本人が読み返すと、頭に残った推論で本文の空白を埋めてしまい、読み手が止まる箇所を見落とすからである。読み直しながら、読み手が止まりそうな箇所を挙げる（何の話か分からない、前提が無い、なぜここで出てくるのか分からない、どちらを指すのか分からない、など）。挙がったら、原因に当たる原則か教訓を特定して直し、直した箇所からもう一度読む。**周回の上限は2。** 2周しても残ったものは、出力の末尾に「未解決」として1〜3行で書く。読み返しの過程そのものは出力に書かない。サブエージェントを使えない環境（チャットアプリなど）では、この項目が別の読み手によるレビューの代わりになる。

## 禁止事項

- **拡大解釈をしない**：論文の主張を超えた一般化、独自解釈の混入をしない
- **断片的な単語列で済ませない**：用語の並列で説明したつもりにならない
- **合成語を未定義のまま使わない**：原則5に従い、初出時に分解する（`不要` の語を除く）
- **読み手が既にイメージできる語を説明しない**：概念の辞書の `不要` の印に従う
- **読み手の個人事情に踏み込まない**：「あなたの研究にとっての含意」のような、読み手の内部状態に依存する内容は書かない
- **必要以上に長くしない**：1セクションは必要な情報量で済ませる
- **コードを要点列挙だけで済ませない**：原則6に従い、ブロックごとに「何を」「なぜ」「裏で何が起きるか」をセットで書く
- **質問への回答を見出しとして追記しない**：原則9に従い、本文を書き直す
- **末尾に「想定される追加質問」を付けない**：運用で参照されていないため廃止した
- **セルフチェックを飛ばさない**：出力前セルフチェックは必須手続き

## このSkillの改訂方針

このSkillは運用の中で改訂される前提で書かれている。改訂の兆候：

- 読み手が「ここが分かりにくい」と指摘した部分
- 読み手が文書中の用語・文の意味を質問することになった（到達基準の不合格＝セルフチェックの検査漏れ）
- 同じ質問を2回以上することになった概念（一度では定着しなかった）
- スクショして残したくならなかった概念図のパターン

これらが見えたら、対応する原則を具体化する。改訂すべき責務が文章スタイルにあるか、出典にあるか、構造にあるかを判断し、適切なSkill（本Skill / `research-citation` / `research-structure`）を更新する。

改訂は思いつきで行わず、**教訓・事例集・表現の辞書を根拠にし、ユーザーが始めたときに行う**。記録の件数などを理由に、エージェントから始めたり提案したりしない。手順は `~/dev-management-private/writing-loop/README.md` の「ルール化」。新しい原則を作る前に既存原則の具体化で済まないかを先に検討する。教訓と事例そのものは本文に書き写さず、教訓から参照させる。
